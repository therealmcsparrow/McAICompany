# `/aico:feature`

`/aico:feature <feature description | draft file>`

## In short
**What it does.** Builds a feature or a whole new product end to end, from brief to shipped. It keeps only the Ship Gate: there is no Brief Gate and no Plan Gate, in any run, a direct call included. Nothing waits for you before the build. What those two Gates used to show (Core and Contract changes, art direction, the task waves, the plan check, the plan review, spike and prototype results, stale paths) is listed in the Ship Gate summary. A decision that used to wait for a Gate is asked as one plain form when it comes up: a `needs-ceo` Handoff, a rule rejected twice, a refused plan check (Fix or Stop), the prototype question (Run it or Skip) and the glossary and ADR drafts (Write or Skip). A script refusal is never bypassed.

**When to use it.** New functionality or a new product — anything that adds or materially changes behavior.

**Help:** `/aico:feature help` (or `--help`) explains the command without running it.

## How it works
1. **Product Manager** writes the brief: problem, users, scope, IDed acceptance criteria. It may add one prototype question, proposed `GLOSSARY.md` entries and proposed ADR drafts, and it can use an earlier research report you name as input. No Brief Gate. One form lists the glossary and ADR lines (Write or Skip; a product with no `GLOSSARY.md` gets one only if you answer Yes to "Create GLOSSARY.md") and asks "Prototype: <question>" with Run it or Skip. Run it answers the question on a throwaway branch before the build, and nothing from it ships. For what a low-risk run may skip, see [short path](../concepts/risk-tier.md).
2. **Architect** ∥ **UI/UX Designer** (if there's UI) ∥ **Brand Artist** (if new art is needed) produce the Core list, Contracts, Module map and wireframes. Persona testers walk the design; the **Senior Engineer** researches or maps the ruleset; the Architect signs it off if Must rules changed. The **Fresh Reviewer** then reads the plan as a newcomer (when the tier set has the plan review and the plan raises a Contract's major version): see [The fresh reviewer](../concepts/review.md). No Plan Gate: the plan check runs and the builders start. Core and Contract changes, art direction and the reviewer's paraphrase and findings (or `plan review: not run`, with `(no Contract major)` when no major was raised) go to the Ship Gate summary.
3. **QA** then **Builders**: QA writes the failing tests first, in every feature run at every tier, and owns those test files ([QA-first](../concepts/plans.md#qa-first-in-feature-runs)). **Builders** build one Module each (in parallel once Contracts are settled), test-first, at the seams the plan names and one slice at a time, following the rules mapped to their tasks. A test that only asserts its own setup is blocked in review. Each task is sized to fit one fresh context ([Plan tasks](../concepts/plans.md)). With `pipeline.worktrees` on, parallel tasks each get a git worktree ([Worktrees](../concepts/parallel-steps.md)). Assets are produced alongside.
4. **Code Reviewer** ∥ **QA** ∥ **Security** ∥ **Senior Engineer** (compliance) review in parallel (at risk `high` with `pipeline.second_reviewer` `on`, plus the **Fresh Reviewer** as a second reviewer; plus **Legal** for AI/payments/personal data, and hands-on + accessibility testers for UI). Blocking findings go back to the builder — at most two Fix rounds by default (set the limit in `/aico:settings`). A review Step that fails twice is recorded as `not run` and shows at the Ship Gate; it never counts as a clean review. If a fix's lines draw a new Blocking finding in the next round, the Fix rounds stop and the Lead asks you.
5. **Writer** adds docs and release notes; **Localizer** translates if you support more than one language. The **Product Manager** writes the destination spec, `docs/specs/<slug>.md` ([Destination spec](../concepts/plans.md)). **→ Ship Gate.** Besides the usual summary it shows the review `not run`, churn and disagreement lines, the rulings and exceptions on file for you to confirm, the spec-check line, two guardrail lines and any leftover worktree.
6. **DevOps** releases as approved.

## Technical details
**Starting tier.** A feature starts at Risk tier medium unless a trusted triage record says low ([Risk tier](../concepts/risk-tier.md)).

**At the Ship Gate.** For a run from a flow build plan, the summary shows every applied approve line printed by `ticket-approval read '<flow slug>'` verbatim with a `> ` prefix, then `tickets changed since approval`. After you approve, the Lead writes the Architect's approved Core list into `.company/project.md` and commits it; until then reviewers judge Core against the list in the Architect's Handoff.

**Draft inputs.** The argument may be a draft file from [`/aico:grill`](grill.md), [`/aico:to-spec`](to-spec.md) or [`/aico:to-tickets`](to-tickets.md): `.company/work/<name>/grill.md`, `spec.md` or `plan.md`. The run reads a copy of it as input and works under a new task name, so your draft is never changed. A `plan.md` draft is checked when the plan is read, and the result goes to the Ship Gate summary because there is no Plan Gate: a path the plan lists that is gone, or that exists now although the plan expected it missing, is a Blocking line, and a path that changed since the plan's base commit is shown for the Architect to weigh. A draft with no base commit line, or one whose base commit is unknown, shows as `stale not checked`. Every other argument starts the run as before: a description, a report path handed over by `research` or `brainstorm`, or a request with its triage line.

**Checks you may meet.** Under `plan_check.policy` `block`, the build start and every task start are refused while the plan has open decisions, and you get a Fix or Stop form ([The hook Gate](../concepts/gates.md)). Reviewers judge the diff from the full base commit; a grafts file stops every judging check, and a binary file in a text path blocks until fixed or excepted by you ([Judging changes](../concepts/review.md)). A security finding never closes by contest. Roles work under their Role id; names are shown only to you. A release carries a `Rollback:` line, an SBOM and a Gate Report ([Releases](../concepts/releases-and-git.md)). The scorecard shows cost only when one is recorded ([Cost from telemetry](../concepts/token-cost.md)).

**You get.** Shipped code on a branch, tests, docs, and the full Handoff trail under `.company/work/<slug>/`.

**Example.** `/aico:feature a dark-mode toggle that remembers the user's choice` · `/aico:feature .company/work/dark-mode/plan.md`
