## Resolution
Per field: project, else user, else plugin. Then the locks:
- `unlocked` counts **only from the user level**. A project `unlocked` is ignored and listed in `ignored`.
- `gates.ship` and `gates.installs` resolve to `auto` only with that key in the user `unlocked`; otherwise `ask`, listed in `ignored`.
- `lanes.security` and `lanes.compliance` resolve to off only with `security` in the user `unlocked`; otherwise on, listed in `ignored`.
- A broken layer (invalid JSON, wrong type, unknown Role, unreadable or too large) falls back to the level below for the bad parts, with a `warnings` line.
- A project layer with any such problem may have lost a re-lock, so it fails closed: `gates.ship` and `gates.installs` are held at `ask` and `lanes.security` and `lanes.compliance` on, whatever the user `unlocked` says, with a `warnings` line. Part M: it also holds `mods.blast_radius` at its plugin defaults and `mods.reflect.mode` `deterministic`.
- **Context cap (v1.1):** a Role's effective cap is `roles.<role>.context_cap` (project, else user), else `pipeline.context_cap` (project, else user), else the plugin default `150000`. `source` says which. `settings.mjs` applies **no** risk rule: the high-risk floor and the 80% handover point live only in pipeline Core (`dispatch-prompt` v3.1 `Context cap:`).
- **Debate style (v1.1):** `brainstorm.debate` resolves per field like any other key (project, else user, else plugin default `crossfire`). It is not a lock: no `unlocked` entry is involved and a fail-closed project layer does not change it.
- **Review format (v1.1, Fix round 6):** `pipeline.review_format` resolves per field like any other key (project, else user, else plugin default `plain`). It is not a lock; a fail-closed project layer does not change it. `pilot` turns on the `handoff` v1.1 pilot (top block, finding rows, findings ledger) for the `code-reviewer` and the `senior-engineer` compliance pass; `plain` keeps the v1.0 Handoff for them. Reason for the default: T15d measured the pilot reviewer at +9.6% spend (n = 6 per arm, 2.6 SE). Builder gains (`Rule slice:`, search-then-read) do not depend on it.
- **Mods (v1.1, part M):** per field like any other key, plus three lock rules:
  1. *The spend switch is user-level only.* `mods.reflect.mode: model` counts only from the user level; a project value is ignored and listed in `ignored` (a cloned repo never spends the CEO's tokens).
  2. *The commit gate only tightens from a project.* A project layer may set `mods.blast_radius.enabled: true` or a category to `ask`; a project `enabled: false` or `warn` is ignored and listed in `ignored`.
  3. *Security stays asked unless unlocked.* `mods.blast_radius.security: warn` and `mods.blast_radius.enabled: false` resolve only with `security` in the user `unlocked`; otherwise `ask` and `true`, listed in `ignored`. `core` and `contract` may be `warn` at the user level without an unlock.
  Plugin defaults for Blast Radius (CEO, part M): `core: ask`, `contract: warn`, `security: ask`. Every other `mods.*` key (each mod's `enabled` except Blast Radius, `pane`, `step_check`, `retrospective`) resolves freely.
- **SkillSpector mode (v1.2):** *the scan's data switch is user-level only.* `skillspector.mode: claude_cli` counts only from the user level; a project `claude_cli` is ignored and listed in `ignored` (`skillspector.mode: claude_cli from project needs the user level`), so a cloned repo never sends skill text to Claude on the CEO's account. A project `no-llm` counts (it only tightens). No `unlocked` entry is involved. Plugin default `no-llm`: no skill text leaves the machine and it costs nothing; package names, versions and ecosystems from a skill's dependency files go to OSV.dev for a vulnerability lookup, plus the ids of any vulnerabilities found (`skillspector-scan` v1 "Network").
- **Personality (v1.3):** per key (`roles.<role>.personality.<key>`): project, else user, else `company/personalities.json`. Not a lock; no `unlocked` entry; a project value counts (CEO, 2026-10-27: quoted, validated data on the social surfaces only). A value that fails its rule (`role-names` v1.1) falls back to the level below with the warning `roles.<role>.personality.<key>: ignored, <reason>`, never echoing the value (AC5). A bad personality value makes the project layer a broken layer, so the fail-closed rule above applies (it only tightens). Resolved only by the exported `resolvePersonalities({ home, cwd, pluginRoot })` → `{ roles: { <role>: { <key>: { value, source: "project"|"user"|"plugin" } } }, warnings, ignored: [{ level: "user"|"project", path, reason }] }` (Fix round 1: the text now names `ignored`, which the code already returns; one entry per refused stored value, no value in it). Its only importers are `scripts/personality.mjs` and `scripts/settings-server.mjs` (a test asserts this).
- **Reprompt question rounds (v1.4):** `reprompt.question_rounds` resolves per field like any other key (project, else user, else plugin default `1`). It is not a lock: no `unlocked` entry is involved, a project value counts (it only bounds how often `/aico:reprompt` asks), and a fail-closed project layer does not change it. A stored value that is not a whole number 0–3 falls back to the level below, with a `warnings` line (broken-layer rule above).
- **Plan check (v1.5):** `plan_check.policy` and `plan_check.runs` resolve per field like any other key (project, else user, else plugin default `warn` and `5`). Neither is a lock: no `unlocked` entry is involved, a project value counts, and a fail-closed project layer does not change them. A stored bad value falls back to the level below, with a `warnings` line.
- **Model floor (v1.6):** rank `haiku` < `sonnet` < `opus`. `fable`, `inherit` and any other value are unranked. A model is below a floor when it is unranked or ranked lower. `settings.mjs` never judges `inherit` (the Lead resolves it first). **Protected lock:** for a Role in `protected`, a resolved `model` of `haiku`, `sonnet` or `fable` below its floor is not applied: `model` = the floor, `source.model` = `floor`, warning `roles.<role>.model: <m> is below the protected floor <f>, not applied` (`<m>` is echoed only when it is `haiku`, `sonnet` or `fable`, else `(other)`). No `unlocked` entry lifts it; a fail-closed project layer does not change it. Floor file missing or invalid at run time (wrong shape, an extra key, a `protected` list that is not exactly the five names, a missing or unranked `floor` entry, over 16 KiB) → every Role `protected: true`, `floor: "opus"`, one warning `model floor: company/model-floor.json unreadable, every Role held at opus`: never fewer protections. `settings.mjs` applies no risk rule; the high-tier floor lives in pipeline Core §2 (`dispatch-prompt` v3.4). Exported `MODEL_RANK` and `loadModelFloor(pluginRoot)` → `{ release, floor, protected, downgraded, warnings }` (`release` is `null` when the file failed); `downgraded` = the Roles whose frontmatter model is below their floor.

A `context_cap` below 60000 (the floor), above 1000000, or not a whole number is refused: `refused: context_cap must be a whole number from 60000 to 1000000`, nothing written.
Any other `brainstorm.debate` value is refused: `refused: brainstorm.debate must be crossfire or full_pass`, nothing written.
Any other `pipeline.review_format` value is refused: `refused: pipeline.review_format must be plain or pilot`, nothing written.
A bad `mods.*` value is refused with `refused: mods.<path> must be <allowed values>`, nothing written.
Any other `skillspector.mode` value, or any other key under `skillspector`, is refused: `refused: skillspector.mode must be no-llm or claude_cli` / `skillspector.<key>: unknown key`, nothing written (v1.2).
A `reprompt.question_rounds` that is not a whole number from 0 to 3, or any other key under `reprompt`, is refused: `refused: reprompt.question_rounds must be a whole number from 0 to 3` / `reprompt.<key>: unknown key`, nothing written (v1.4).
A `plan_check.policy` other than off, warn or block, a `plan_check.runs` that is not a whole number from 3 to 50, or any other key under `plan_check`, is refused: `refused: plan_check.policy must be off, warn or block` / `refused: plan_check.runs must be a whole number from 3 to 50` / `plan_check.<key>: unknown key`, nothing written (v1.5).
**Personality refusals (v1.3), path first:** every refusal about a personality value is one line that starts with the full dotted path, then `: `, so the page can mark the exact field. The value is never echoed. Exactly:
- `roles.<role>.personality: must be an object`
- `roles.<role>.personality.<key>: unknown key` (the key shown only when it matches `^[a-z_]{1,20}$`, else `?`)
- `roles.<role>.personality.<temperament|talk|topic>: must be 1 to 80 characters`
- `roles.<role>.personality.<temperament|talk|topic>: must be one line of letters, digits, single spaces and , . ' - ! ?; each word starts with a letter or digit`
- `roles.<role>.personality.<intelligence|creativity>: must be low, medium or high`
A save is still all or nothing: any refused line → nothing written. The CLI prints `refused: ` before each line; the server returns them, without that prefix, in its `refused` array (as today). As for every layer refusal today (`checkLayers`), a server line is preceded by its level word and one space (`user ` or `project `), then the path; the page maps level plus path to the field. The page builds the richer field text (character count, the offending character, a word that does not start with a letter or digit, an invisible or lookalike character) from its own copy of the value, never from the server line.
**Stored bad personality values on Save (v1.3, Step 07):** the server checks personality values only in the layers the Save body carries. A personality value already stored in a layer the body does not carry is a load warning (`ignored`), never a save refusal, so a bad value in a cloned project file never blocks an unrelated Save. Cross-layer checks (name clashes) are unchanged.

`brainstorm.debate` picks how a **debate** round runs (`brainstorm-file` v2, `brainstorm-reply` v1):
- `crossfire`: the ideas pass only; the strongest challenge (the crossfire pair) is answered by the idea's author in the next round's ideas pass, with no extra dispatch (Fix round 4, `docs/adr/0014-crossfire-folded-into-next-round.md`; before: one extra dispatch per pair member in the same round).
- `full_pass`: the ideas pass, then a full pass (every Role answers the others' replies of that round), then the crossfire pair on top, dispatched in the same round.
It has no effect on `ideas` or `moderated` rounds. Values and default are unchanged by Fix round 4.

Warnings also go to stderr as `warning: <text>`.
**`model-env` (v1.6):** no process starts unless a variable is set. Then it reads the Claude Code version: `AI_AGENT` (`claude-code_<major>-<minor>-<patch>_…`, no process) and `claude --version`. `claude` is resolved by walking `PATH` for an absolute entry only; an empty entry, a relative entry, and an entry that is or lies inside the current folder or the product root are skipped, and the found absolute path runs with the temp folder as its working directory (no shell, 5 s limit, 4 KiB output, first `\d{1,4}\.\d{1,4}\.\d{1,4}`); no hit → that source is unread. Without FORCE the lower of two differing versions is used; neither → unknown. With FORCE on, `floor kept` needs both sources read, equal and below 2.1.257: any disagreement or a single source is unknown and counts as `bypassed`. It prints one line:
`model env: CLAUDE_CODE_SUBAGENT_MODEL=<v> CLAUDE_CODE_SUBAGENT_MODEL_FORCE=<f>, Claude Code <ver|unknown>: <effect>; floor <kept|bypassed>`
`<v>`/`<f>`: the value when it matches `^[A-Za-z0-9._:\[\]-]{1,64}$`, `unset`, else `(hidden)`. First match wins:
1. version unknown → `version unknown, may override every Role's model`; `bypassed`.
2. below 2.1.251 and the variable set → `overrides every Role's model, the Agent model included`; `bypassed`.
3. 2.1.257 or later and FORCE on → `forces <v> on every Role` (variable unset: `forces the main conversation's model on every Role`); `bypassed` (whether FORCE beats the Agent `model` is unverified, so it counts as a bypass).
3b. FORCE on and the two sources not both read and equal → `version not confirmed by both sources, FORCE may force a model on every Role`; `bypassed`; the version prints as `unknown`.
4. the variable set → `a default only; every aico Role sets model in its frontmatter, so no Role changes`; `kept`.
5. FORCE on only → `FORCE needs Claude Code 2.1.257; no Role changes`; `kept`.

2. **Personality tab.** It holds the whole personality section (moved from the Roles tab; behaviour as in v1.3 and Step 07). At its top a **Role filter**: a text input with the visible label "Filter Roles" and the hint "Name, Role or department". It matches case-insensitively, as a substring, against each Role's slug, effective name and department label, and hides the cards that do not match (`hidden`). Under it a count line, its own small `role="status"` region: "Showing <n> of <total> Roles", or "No Role matches the filter." at 0. The filter only hides: hidden cards keep their drafts and errors and are saved like the rest; the filter text is never saved or sent. Department labels are `<h3>`. Each fieldset legend names the Role and the level ("Ava (architect), User level"), so a group is never announced without its Role.
3. **Status at the top.** The page's status region (`#status`, `role="status"`, `aria-live="polite"`) sits directly under the page header and above the tab list, so it is in view on every tab without scrolling. The sticky footer keeps the change count and the Save, Reset and Done buttons.
4. **Refused Save.** The status shows an error summary: a heading "Nothing was saved. Fix <n> field(s):" (`tabindex="-1"`), then one list item per refused line. A line that maps to a field is a link (`href="#<field id>"`) with the text `<Name> (<role>), <level> level, <field label>: <problem>` (the page's own richer text). Focus moves to the heading. Activating a link selects the field's tab, clears the Role filter when it hides that Role, opens the Role's `<details>`, then focuses the field and scrolls it into view. A line that maps to no field (a stale revision, a name clash) is plain text. This replaces v1.3's "focuses the first" refused field.
5. **Focus after a reload.** After a successful Save or a stale-revision reload the page rebuilds its panels, then focuses the element with the same `id` as the one that had focus before, when it still exists, is visible and is enabled; otherwise the status message (`tabindex="-1"`: "Saved." or the stale-revision text). Done focuses the "Settings server stopped" message. Focus never ends on `body`. Every control the page builds has a stable `id`: `pf-<role>-<level>-<key>` for personality fields (as today) and `rf-<role>-<level>-<name|model|effort|cap>` for the Roles table.
6. **No horizontal scrolling at any width.** At every viewport width from 320 CSS px up (this covers 400% zoom of a 1280 px window) and at 200% zoom, neither the page nor any element on it scrolls sideways: `document.documentElement.scrollWidth <= window.innerWidth`, and no element has `scrollWidth > clientWidth` with a computed `overflow-x` of `auto` or `scroll`. So: no `overflow-x: auto | scroll` in the page CSS, no table with a fixed `min-width`, no `position: sticky` table cell. A table stays a table while it fits its box; below that (a container or media query, the builder's choice) each row is a stacked card: the row header first (the Role name), then each cell with its column header as a visible label. Values wrap (`overflow-wrap: anywhere`); controls shrink to the card width. This holds on every tab, the Roles table included.
7. **Roles table labels.** Each per-level control (name, model, effort, cap) has a visible `<label for>`, in the cell, whose text starts with the field word ("Name", "Model", "Effort", "Cap"), followed by visually hidden context ", <Name> (<role>), <level> level". No `aria-label` on these controls, and a placeholder is never the label (WCAG 1.3.1, 2.5.3, 3.3.2).
8. **Bulk bar.** "Apply to" and "at" are the controls' only names (their wrapping `<label>`); no `aria-label` (2.5.3).
9. **Focus not obscured (2.4.11).** No sticky column exists (rule 6). The sticky footer never covers a focused control: the scrolling root has `scroll-padding-bottom` at least the footer's height.

## How the pipeline uses it (`aico:pipeline`)
- Setup §1.7 runs `get` once per run (fixed command) and keeps the JSON; never re-resolved mid-run.
- Setup §1.7 runs `model-env` once per run (fixed command); §2 applies the floor from `get` `floor` and `protected` (v1.6).
- Model and effort: passed on the Agent call only when they differ from the agent frontmatter. `inherit` means the Lead's session model: the Lead passes its session model family (`opus | sonnet | haiku | fable`), never the literal `inherit` and never an omitted `model` (that falls back to the frontmatter). Recorded in the `Settings:` dispatch line (`dispatch-prompt` v3).
- `pipeline.fix_rounds` is the Fix-round limit; at 0 the first blocking review goes to the CEO. `sequential` dispatches the ∥ Steps one at a time.
- `pipeline.review_format: pilot` → the Lead adds `Review format: pilot` to every `code-reviewer` dispatch and every `senior-engineer` compliance dispatch (`dispatch-prompt` v3.1) and lints those Handoffs with `--require-top`. `plain` → no such line and the plain lint (`handoff` v1.1, "Pilot scope").
- Lanes gate the optional lanes in `feature`, `fix`, `maintain` and `refactor`; lanes a Playbook always runs are unaffected. A company type's `ship.lanes` (`company-type` v1) are forced on for its Ship, whatever these say.
- `auto` Gates write their summary to the run folder and continue. Never auto, whatever the settings: `needs-ceo`, Blocking security findings, picks, escalations, design-skill set approval, client sends, publishing, authority reports, production deploys. An auto Ship Gate first runs the Finish writes and commits (summary, Debt, Lessons), then pushes the branch and opens a PR, then stops; it never merges.
- `roles.<role>.context_cap` becomes the `Context cap:` dispatch line after the pipeline applies the high-risk floor and the 80% handover point (`dispatch-prompt` v3.1).
- `brainstorm.film_script` is read by `aico:brainstorm` (`brainstorm-file` v2); `true` renders the film script file at each round.
- `brainstorm.debate` is read by `aico:brainstorm` from the run's `get` JSON (never re-resolved mid-run) and written into each debate round's heading (`brainstorm-file` v2), so the file records which style ran.
- `mods.*` is never read by the pipeline. The mods run `get` themselves at session start and at each main-loop turn start (`aico-mods` v1), so a change takes effect by the next turn.
- `skillspector.mode` is never read by the pipeline. `scripts/skillspector.mjs` runs `get skillspector.mode` itself when no `--mode` flag is given (`skillspector-scan` v1); any failure means `no-llm`.
- `roles.<role>.personality.*` is never read by the pipeline or the Lead (v1.3). It is not in `get`; `personality.mjs` and `brainstorm.mjs stage` turn it into the `role-names` v1.1 block in a file only the dispatched social Role reads.
- `reprompt.question_rounds` (v1.4) is read only by `aico:reprompt`, from the run's §1.7 `get` JSON (never re-resolved mid-run). It caps the question rounds of one reprompt run and becomes the first `Asks left:` value (`dispatch-prompt` v3.3). Absent, or not an integer 0–3 → `1`.
- `plan_check.policy` (v1.5) is read by the Lead at each Plan Gate from the run's §1.7 `get` JSON (never re-resolved mid-run) and passed to `plan-check.mjs` (`plan-check` v1). `plan_check.runs` is read only by `aico:feedback` and passed to `plan-check-verdict.mjs verdict --runs`. Absent or invalid → `warn` and `5`.

## Error cases
- `get` exits non-zero or prints invalid JSON → the pipeline uses plugin defaults and says so in the first Gate summary and in its first chat message. Plugin defaults include `context_cap` 150000, `review_format` `plain`, `film_script` false and `debate` `crossfire`. The mods use `MODS_DEFAULTS` (all on, Reflect deterministic, Blast Radius `core: ask`, `contract: warn`, `security: ask`) and show `settings unknown` in their status line. `skillspector.mjs` uses `no-llm`. `aico:reprompt` uses `question_rounds` 1 and says so once (v1.4). The Plan Gate uses policy `warn` and /aico:feedback runs 5 (v1.5).
- Invalid value, unknown key or a stale `revision` on save: `refused: <reason>` (exit 2 on the CLI, 4xx from the server), nothing written.
- Unknown subcommand or extra arguments: `refused: usage: settings.mjs get [key] | serve [--no-open] | model-env` (exit 2).
- `get <key>` for a missing key: `refused: no setting <key>` (exit 2).
- A layer with a bad `context_cap`, `brainstorm.debate`, `pipeline.review_format`, `mods.*`, `skillspector.mode`, (v1.4) `reprompt.question_rounds`, (v1.5) `plan_check.policy` or `plan_check.runs` value → that field falls back to the level below, with a `warnings` line (broken-layer rule above).
- (v1.3) A layer with a bad personality value → that key falls back to the level below, warning without the value; `company/personalities.json` unreadable or invalid at run time → `resolvePersonalities` uses no personality for the bad entries and warns, and `personality.mjs` renders nothing for such a Role (the Role speaks without one); `check.mjs` blocks such a file in CI.
