## Storage
- **User:** `<MCSPARROW_HOME or ~/.mcsparrow>/config.json`, key `aico_settings`. Other keys, including `aico_language`, are preserved on write.
- **Project:** `.company/settings.json`, holding `{ "aico_settings": … }`.
- **Plugin:** model and effort from `agents/*.md` frontmatter, names from `company/names.json` (`role-names` v1), personalities from `company/personalities.json` (`role-names` v1.1), `PIPELINE_DEFAULTS` (v1.7: gains `parallel_cap: 4`; v1.8: gains `short_path: "on"`; v1.10: gains `second_reviewer: "off"`, `second_reviewer_model: "default"`, `worktrees: "off"`), `GATE_DEFAULTS`, `BRAINSTORM_DEFAULTS`, `MODS_DEFAULTS`, `SKILLSPECTOR_DEFAULTS` (v1.2), `REPROMPT_DEFAULTS = { question_rounds: 1 }` (v1.4) and `PLAN_CHECK_DEFAULTS = { policy: "warn", runs: 5 }` (v1.5) in `settings.mjs`.
- **Plugin, model floor (v1.6):** `company/model-floor.json` = `{ "v": 1, "release": "0.16.0", "floor": { "<role>": "haiku|sonnet|opus", … }, "protected": ["architect", "code-reviewer", "fresh-reviewer", "pentester", "security", "vuln-scanner"] }`, at most 16 KiB, exactly those four keys, one `floor` entry per Role, `protected` exactly those six names (v1.10: `fresh-reviewer` added; a stored `roles.fresh-reviewer.model` below `opus` is not applied at any tier, so the second reviewer's default model is never below `opus`) (rationale `docs/adr/0031-model-floor-table.md`). `scripts/check.mjs` validates it.

## Resolution
Per field: project, else user, else plugin. Then the locks:
- `unlocked` counts **only from the user level**. A project `unlocked` is ignored and listed in `ignored`.
- `gates.ship` and `gates.installs` resolve to `auto` only with that key in the user `unlocked`; otherwise `ask`, listed in `ignored`.
- `lanes.security` and `lanes.compliance` resolve to off only with `security` in the user `unlocked`; otherwise on, listed in `ignored`.
- A broken layer (invalid JSON, wrong type, unknown Role, unreadable or too large) falls back to the level below for the bad parts, with a `warnings` line.
- A project layer with any such problem may have lost a re-lock, so it fails closed: `gates.ship` and `gates.installs` are held at `ask` and `lanes.security` and `lanes.compliance` on, whatever the user `unlocked` says, with a `warnings` line. Part M: it also holds `mods.blast_radius` at its plugin defaults and `mods.reflect.mode` `deterministic`.
- **Context cap (v1.1, deprecated in v1.11):** every Role's reported cap and `pipeline.context_cap` are the fixed `95000`, `source.context_cap` is `plugin`. A stored `roles.<role>.context_cap` or `pipeline.context_cap` is validated like before but has no effect on the reported value and is never read by the pipeline. `settings.mjs` applies no risk rule.
- **Debate style (v1.1):** `brainstorm.debate` resolves per field like any other key (project, else user, else plugin default `crossfire`). It is not a lock: no `unlocked` entry is involved and a fail-closed project layer does not change it.
- **Review format (v1.1, Fix round 6):** `pipeline.review_format` resolves per field like any other key (project, else user, else plugin default `plain`). It is not a lock; a fail-closed project layer does not change it. `pilot` turns on the `handoff` v1.1 pilot (top block, finding rows, findings ledger) for the `code-reviewer` and the `senior-engineer` compliance pass; `plain` keeps the v1.0 Handoff for them. Reason for the default: T15d measured the pilot reviewer at +9.6% spend (n = 6 per arm, 2.6 SE). Builder gains (`Rule slice:`, search-then-read) do not depend on it.
- **Mods (v1.1, part M):** per field like any other key, plus three lock rules:
  1. *The spend switch is user-level only.* `mods.reflect.mode: model` counts only from the user level; a project value is ignored and listed in `ignored` (a cloned repo never spends the CEO's tokens).
  2. *The commit gate only tightens from a project.* A project layer may set `mods.blast_radius.enabled: true` or a category to `ask`; a project `enabled: false` or `warn` is ignored and listed in `ignored`.
  3. *Security stays asked unless unlocked.* `mods.blast_radius.security: warn` and `mods.blast_radius.enabled: false` resolve only with `security` in the user `unlocked`; otherwise `ask` and `true`, listed in `ignored`. `core` and `contract` may be `warn` at the user level without an unlock.
  Plugin defaults for Blast Radius (CEO, part M): `core: ask`, `contract: warn`, `security: ask`. Every other `mods.*` key (each mod's `enabled` except Blast Radius, `pane`, `step_check`, `retrospective`) resolves freely.
- **SkillSpector mode (v1.2):** *the scan's data switch is user-level only.* `skillspector.mode: claude_cli` counts only from the user level; a project `claude_cli` is ignored and listed in `ignored` (`skillspector.mode: claude_cli from project needs the user level`), so a cloned repo never sends skill text to Claude on the CEO's account. A project `no-llm` counts (it only tightens). No `unlocked` entry is involved. Plugin default `no-llm`: no skill text leaves the machine and it costs nothing; package names, versions and ecosystems from a skill's dependency files go to OSV.dev for a vulnerability lookup, plus the ids of any vulnerabilities found (`skillspector-scan` v1 "Network").
- **Personality (v1.3):** per key (`roles.<role>.personality.<key>`): project, else user, else `company/personalities.json`. Not a lock; no `unlocked` entry; a project value counts (CEO, 2026-10-27: quoted, validated data on the social surfaces only). A value that fails its rule (`role-names` v1.1) falls back to the level below with the warning `roles.<role>.personality.<key>: ignored, <reason>`, never echoing the value (AC5). A bad personality value makes the project layer a broken layer, so the fail-closed rule above applies (it only tightens). Resolved only by the exported `resolvePersonalities({ home, cwd, pluginRoot })` → `{ roles: { <role>: { <key>: { value, source: "project"|"user"|"plugin" } } }, warnings, ignored: [{ level: "user"|"project", path, reason }] }` (Fix round 1: the text now names `ignored`, which the code already returns; one entry per refused stored value, no value in it). Its only importers are `scripts/personality.mjs` and `scripts/settings-server.mjs` (a test asserts this).
- **Reprompt question rounds (v1.4):** `reprompt.question_rounds` resolves per field like any other key (project, else user, else plugin default `1`). It is not a lock: no `unlocked` entry is involved, a project value counts (it only bounds how often `/aico:reprompt` asks), and a fail-closed project layer does not change it. A stored value that is not a whole number 0–3 falls back to the level below, with a `warnings` line (broken-layer rule above).
- **Plan check (v1.5, policy v1.9):** `plan_check.runs` resolves per field like any other key (project, else user, else plugin default `5`); no `unlocked` entry is involved. `plan_check.policy` follows *block wins*: a `block` in the user layer resolves to `block`, and a project `off` or `warn` over it is ignored and listed in `ignored` (`plan_check.policy: a project cannot lower a user block`). A project `block` counts (it only tightens). A broken project layer is an empty layer, so it never lowers a user `block`. Otherwise the policy resolves per field (project, else user, else `warn`). A stored bad value falls back to the level below, with a `warnings` line.
- **Model floor (v1.6):** rank `haiku` < `sonnet` < `opus`. `fable`, `inherit` and any other value are unranked. A model is below a floor when it is unranked or ranked lower. `settings.mjs` never judges `inherit` (the Lead resolves it first). **Protected lock:** for a Role in `protected`, a resolved `model` of `haiku`, `sonnet` or `fable` below its floor is not applied: `model` = the floor, `source.model` = `floor`, warning `roles.<role>.model: <m> is below the protected floor <f>, not applied` (`<m>` is echoed only when it is `haiku`, `sonnet` or `fable`, else `(other)`). No `unlocked` entry lifts it; a fail-closed project layer does not change it. Floor file missing or invalid at run time (wrong shape, an extra key, a `protected` list that is not exactly the six names, a missing or unranked `floor` entry, over 16 KiB) → every Role `protected: true`, `floor: "opus"`, one warning `model floor: company/model-floor.json unreadable, every Role held at opus`: never fewer protections. `settings.mjs` applies no risk rule; the high-tier floor lives in pipeline Core §2 (`dispatch-prompt` v3.4). Exported `MODEL_RANK` and `loadModelFloor(pluginRoot)` → `{ release, floor, protected, downgraded, warnings }` (`release` is `null` when the file failed); `downgraded` = the Roles whose frontmatter model is below their floor.
- **Parallel cap (v1.7):** `pipeline.parallel_cap` resolves per field like any other key (project, else user, else plugin default `4`). Not a lock: no `unlocked` entry, a project value counts, and a fail-closed project layer does not change it. A stored value that is not a whole number from 3 to 5 falls back to the level below, with a `warnings` line (broken-layer rule above). `settings.mjs` applies no dispatch rule: `pipeline.dispatch: sequential` overriding the cap lives in pipeline Core (`skills/pipeline/references/parallel.md`, `plan-tasks` v1).
- **Second reviewer, model and worktrees (v1.10), user level only:** `pipeline.second_reviewer`, `pipeline.second_reviewer_model` and `pipeline.worktrees` count only from the user level. Any project value is ignored and listed in `ignored` (`pipeline.second_reviewer: set it at the user level`, `pipeline.second_reviewer_model: set it at the user level`, `pipeline.worktrees: set it at the user level`); a fail-closed project layer does not change them. A stored value that does not count (a bad `on`/`off`; a model that is not `default` or is unranked or below the `code-reviewer` floor from `company/model-floor.json`, ADR 0031: `haiku` < `sonnet` < `opus`, `fable` unranked) resolves as the default with a `warnings` line. `get` `pipeline` holds `second_reviewer`, `second_reviewer_model` (the stored value) and `second_reviewer_model_effective`: `default` resolves to the resolved `roles.fresh-reviewer.model` with its floor applied (never below `opus`, also when a project sets that Role's model lower, because `fresh-reviewer` is protected); any other value is itself. The model floor file unreadable or invalid → effective `opus` (fail closed, as v1.6). No `unlocked` entry is involved. `settings.mjs` runs nothing: the Lead reads the values (see "How the pipeline uses it").
- **Short path (v1.8), off wins:** `off` at the user or the project level resolves to `off`. A project `on` while the user level is `off` is ignored and listed in `ignored` (`pipeline.short_path: a project can only turn the short path off`). A fail-closed project layer holds it `off` (add it to that rule's list). A stored value other than `on` or `off` falls back to the level below with a `warnings` line. No `unlocked` entry is involved. `settings.mjs` applies no tier rule: the sets live in `company/tier-sets.json` (`tier-sets` v1).
- **Role skills (v1.12):** `roles.<role>.skills` is a list of at most 5 `{ name, approved }` selections, and a list is one field: a project list replaces the user list for that Role, and absent at both levels means no skills. A selection is a lookup key into `skill-catalog` v1; nothing else is read from it, and a project supplies no entry, command or path. The level that supplied the list is `source.skills` (`project` or `user`; `plugin` when no list counts) and sets the install scope (`skill-catalog` "Status").
  1. *Stale names.* A stored name not in the catalog, not eligible for that Role's categories, or not selectable (a wildcard), and a repeated name, is dropped and listed in `ignored` by field path (`roles.<role>.skills[<n>].name: not selectable for this Role`), never its value. It does not make the project layer broken, so a clone's stale name never holds Gates at ask.
  2. *Fallback.* A project list whose names are all ignored falls back to the user list for that Role. So does any project list for a protected Role, an empty one included, listed in `ignored` (`roles.<role>.skills: a project cannot set this for a protected Role`); with the floor file unreadable every Role counts as protected (v1.6). Otherwise an explicit `[]` replaces the user list: it holds no stale name and is a visible choice.
  3. *Wrong shape.* A value that is not a list, a list over 5, an entry that is not an object, or an unknown key in an entry falls back to the level below with the warning `roles.<role>.skills: ignored, <reason>`, never echoing a value. In the project layer it makes the layer broken, so the fail-closed rule above applies (it only tightens).
  4. *Settings folder check.* `get` prints top-level `settings_folder_moved`: `true` when the settings folder does not resolve to `<os.userInfo().homedir>/.mcsparrow`, whichever env moved it (`MCSPARROW_HOME`, `HOME`, `USERPROFILE`), or when the user home cannot be read; else `false`. While it is `true` the user-level lists are not counted, one `warnings` line says so, and `--selected` takes no `gates.installs: auto` answer (`skill-catalog` "Layers"). Other settings and `/aico:setup` are unchanged by it. A reader that gets no boolean counts it as `true`.
  5. *`approved`.* On a Save the server sets `approved` to today on every selection of each Role whose list changes at that level (a name added or removed; order alone is no change); other Roles keep their dates, and an `approved` in a Save body is not used. A researcher record (`skill-recommendation` v2.0) sets today on the selections it records, even unchanged. Migration keeps the old date. A missing, invalid or future date is no date: `get` prints `approved` `null`. The page has no re-approve control. `approved` is freshness only: it decides whether a research Step runs, and it never replaces or answers the Install form (agentsec.M-SEC4, proj.M-SEC8).
  Not a lock: no `unlocked` entry is involved.

## How the pipeline uses it (`aico:pipeline`)
- Setup §1.7 runs `get` once per run (fixed command) and keeps the JSON; never re-resolved mid-run.
- Setup §1.7 runs `model-env` once per run (fixed command); §2 applies the floor from `get` `floor` and `protected` (v1.6).
- Model and effort: passed on the Agent call only when they differ from the agent frontmatter. `inherit` means the Lead's session model: the Lead passes its session model family (`opus | sonnet | haiku | fable`), never the literal `inherit` and never an omitted `model` (that falls back to the frontmatter). Recorded in the `Settings:` dispatch line (`dispatch-prompt` v3).
- `pipeline.fix_rounds` is the Fix-round limit; at 0 the first blocking review goes to the CEO. `sequential` dispatches the ∥ Steps one at a time.
- `pipeline.review_format: pilot` → the Lead adds `Review format: pilot` to every `code-reviewer` dispatch and every `senior-engineer` compliance dispatch (`dispatch-prompt` v3.1) and lints those Handoffs with `--require-top`. `plain` → no such line and the plain lint (`handoff` v1.1, "Pilot scope").
- Lanes gate the optional lanes in `feature`, `fix`, `maintain` and `refactor`; lanes a Playbook always runs are unaffected. A company type's `ship.lanes` (`company-type` v1) are forced on for its Ship, whatever these say.
- `auto` Gates write their summary to the run folder and continue. Never auto, whatever the settings: `needs-ceo`, Blocking security findings, picks, escalations, design-skill set approval, client sends, publishing, authority reports, production deploys. An auto Ship Gate first runs the Finish writes and commits (summary, Debt, Lessons), then pushes the branch and opens a PR, then stops; it never merges.
- `context_cap` is not read (v1.11): the `Context cap:` dispatch line is the fixed `95000 handover 85500` (`dispatch-prompt` v4.2).
- `brainstorm.film_script` is read by `aico:brainstorm` (`brainstorm-file` v2); `true` renders the film script file at each round.
- `brainstorm.debate` is read by `aico:brainstorm` from the run's `get` JSON (never re-resolved mid-run) and written into each debate round's heading (`brainstorm-file` v2), so the file records which style ran.
- `mods.*` is never read by the pipeline. The mods run `get` themselves at session start and at each main-loop turn start (`aico-mods` v1), so a change takes effect by the next turn.
- `skillspector.mode` is never read by the pipeline. `scripts/skillspector.mjs` runs `get skillspector.mode` itself when no `--mode` flag is given (`skillspector-scan` v1); any failure means `no-llm`.
- `roles.<role>.personality.*` is never read by the pipeline or the Lead (v1.3). It is not in `get`; `personality.mjs` and `brainstorm.mjs stage` turn it into the `role-names` v1.1 block in a file only the dispatched social Role reads.
- `reprompt.question_rounds` (v1.4) is read only by `aico:reprompt`, from the run's §1.7 `get` JSON (never re-resolved mid-run). It caps the question rounds of one reprompt run and becomes the first `Asks left:` value (`dispatch-prompt` v3.3). Absent, or not an integer 0–3 → `1`.
- `plan_check.policy` (v1.5) is read by the Lead at each Plan Gate from the run's §1.7 `get` JSON (never re-resolved mid-run) and passed to `plan-check.mjs` (`plan-check` v1). `plan_check.runs` is read only by `aico:feedback` and passed to `plan-check-verdict.mjs verdict --runs`. Absent or invalid → `warn` and `5`.
- `pipeline.parallel_cap` (v1.7) is read by the Lead from the run's §1.7 `get` JSON (never re-resolved mid-run) and passed to `plan-tasks.mjs` as `--cap`; at most that many Steps of a pipeline Playbook run at once (`skills/pipeline/references/parallel.md`). `pipeline.dispatch: sequential` overrides it with 1. Absent or invalid → 4.
- `pipeline.short_path` (v1.8) is read by the Lead from the run's §1.7 `get` JSON (never re-resolved mid-run) and passed to `tier-set.mjs` as `--short`. Absent, invalid or no `get` JSON → `off`.
- `pipeline.second_reviewer` and `pipeline.second_reviewer_model_effective` (v1.10) are read by the Lead from the run's §1.7 `get` JSON (never re-resolved mid-run). The route entry `second-reviewer` (`tier-sets` v1.2) runs only at run tier `high` with `second_reviewer` `on`; the second reviewer is dispatched on `second_reviewer_model_effective`, passed on the Agent call per the model rule and recorded on `Settings:`. `pipeline.worktrees` is read the same way; `on` is one of the conditions for the worktree flow. Absent, invalid or no `get` JSON → `off` for both, and the model `opus`.
- `settings_folder_moved` (v1.12) is read by the Lead from the run's §1.7 `get` JSON (never re-resolved mid-run), for the `gates.installs: auto` answer. The Lead builds the `Role skills:` dispatch line from `install-skills --status`, not from `roles.<role>.skills` in that JSON (`dispatch-prompt`, `skill-catalog` v1 "Selected install"). `install-skills.mjs --selected` and `--status` run `get` themselves. Absent, invalid or no `get` JSON → no selections and `settings_folder_moved` `true`.

## Error cases
- `get` exits non-zero or prints invalid JSON → the pipeline uses plugin defaults and says so in the first Gate summary and in its first chat message. Plugin defaults include `context_cap` 95000, `review_format` `plain`, `film_script` false and `debate` `crossfire`, (v1.7) parallel cap 4 and (v1.8) "short path off" (the one default that differs from `PIPELINE_DEFAULTS`, because the fallback must never shorten a run). The mods use `MODS_DEFAULTS` (all on, Reflect deterministic, Blast Radius `core: ask`, `contract: warn`, `security: ask`) and show `settings unknown` in their status line. `skillspector.mjs` uses `no-llm`. `aico:reprompt` uses `question_rounds` 1 and says so once (v1.4). The Plan Gate uses policy `warn` and /aico:feedback runs 5 (v1.5).
- Invalid value, unknown key or a stale `revision` on save: `refused: <reason>` (exit 2 on the CLI, 4xx from the server), nothing written.
- Unknown subcommand or extra arguments: `refused: usage: settings.mjs get [key] | serve [--no-open] | model-env` (exit 2).
- `get <key>` for a missing key: `refused: no setting <key>` (exit 2).
- A layer with a bad `context_cap`, `brainstorm.debate`, `pipeline.review_format`, `mods.*`, `skillspector.mode`, (v1.4) `reprompt.question_rounds`, (v1.5) `plan_check.policy` or `plan_check.runs`, (v1.7) `pipeline.parallel_cap`, (v1.8) `pipeline.short_path`, (v1.10) `pipeline.second_reviewer`, `pipeline.second_reviewer_model` or `pipeline.worktrees` value → that field falls back to the level below, with a `warnings` line (broken-layer rule above).
- (v1.3) A layer with a bad personality value → that key falls back to the level below, warning without the value; `company/personalities.json` unreadable or invalid at run time → `resolvePersonalities` uses no personality for the bad entries and warns, and `personality.mjs` renders nothing for such a Role (the Role speaks without one); `check.mjs` blocks such a file in CI.
- (v1.12) A stored stale name in `roles.<role>.skills` is listed in `ignored` and never dispatched; it is not a broken layer. A wrong shape falls back as Resolution "Role skills" rule 3 says. The catalog unreadable → every stored name counts as stale, and no value is echoed.
