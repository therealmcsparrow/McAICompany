# Contract: context-guard v3.0

v3.0 (task P20261117.000001/01-feature, major, breaking; ADR `docs/adr/0077-lead-as-subagent.md`, ADR `docs/adr/0079-guards-leave-shell-alone.md`; Lead is the plugin agent `aico:project-manager`, `hook-event` v1.4). Replaces every v2.x clause it names; the rest of v2.x stands:
- The Lead branch applies to the Lead agent (session `lead` with an `agentKey`); main (session `lead`, `agentKey` null) is never capped, at any token level. The clean point deny reason tells the Lead to end with `STATUS: handover` plus its `handoff:` and `next:` lines. Frozen denies every tool: the MCP tool name and `SendFeedback` leave the allow-list. `bg` rows are removed. Frozen and the clean point end a Lead or Role by denying tools, never by `continue:false` (a `continue:false` stop emits no `SubagentStop`).
- Order in the Lead branch at and over `F`: Frozen, then Step running, then the clean point. "Step running" is unchanged: it denies `Agent` and `Task` with the wait reason, other tools pass; it now catches only a Step whose `SubagentStop` was missed.
- Spawn limits, judged by `cap.M1` before any fast-floor return, at every token level, and not needing the run unless named:
  - In an active run main may spawn only `aico:project-manager` (`cap.M1: main spawns only the Lead`).
  - An `Agent` or `Task` call whose `subagent_type`, folded to lower case, is `project-manager` or ends in `:project-manager`, from any payload with `agent_id` whose `agent_type` is not exactly `aico:project-manager` (a Role, any depth, also a foreign, look-alike or missing `agent_type`), is denied with or without an active run (`cap.M1: a Role never spawns the Lead`). A Lead agent may spawn a helper Lead, foreground only.
  - Main's call to `aico:project-manager` with `run_in_background` true is denied with or without an active run (`cap.M1: main runs the Lead in the foreground`).
  - In an active run a Lead agent call with `run_in_background` true is denied (`cap.M1: the Lead dispatches Roles in the foreground`), so no Role outlives its Lead.
- Protected run records: `forms.jsonl` and `run-state.jsonl` join `guard.jsonl` (Write/Edit and `Bash`/`PowerShell` writes, any session), matched by path shape `/.company/work/<parts>/<guard|forms|run-state>.jsonl`, so `run` is not needed.
- `AICO_GUARDS=off` (CEO only) drops the guards for session `lead` only, main and the Lead agent: every guard verdict of that session is dropped as before (the two background denies too), except the run-record write deny. Roles (session `step`) stay guarded, so the Role `project-manager` spawn deny is never dropped. The run records stay shielded; `preset` is the other check `off` never drops.
- Shell commands: `self-protect.M-SEC1` judges a `Bash` or `PowerShell` command only for a write to a run record (the shell write analysis stays, its target set shrinks to the run-record shape). Plugin, settings, McSparrow-home and `hook-pins`/`set-mod` shell commands pass in every session. A target the analysis cannot resolve (a variable such as `$p`, an `-EncodedCommand` that decodes to no record path) is not a run-record write and passes, with one exception: when the command text (or the subshell holding the write) names a run-record path, a write to a variable or `$(...)` target in it is denied, since the record path may be bound to that variable in the same command (`p=<rec>/guard.jsonl; echo hi > $p` denies; `echo hi > $p` alone passes). Fail closed for the run-record check: an over-long command (over 200000 chars) is denied, and so is a brace expansion that reaches the expansion limit (not any brace). `Write` and `Edit` protection of plugin and settings files is unchanged.

v2.2 (task P20261114.000002/02-fix, minor, CEO decision "Keep + bump contracts"; code review R-2, security R-1). Narrows the `bg` rule of v2.1; no other change:
- With `AICO_GUARDS=off` (CEO only) the host writes no `bg` row (the gate at `scripts/hook-host.mjs` runs only when guards are on). A call the host denies before the gate, such as a failed or invalid snapshot, also writes none. So the former lead-replace script (removed) sees no background task for that session and does not wait for it; with guards off a hand-over may start while a background task still runs. The v2.1 words "also with `AICO_GUARDS=off`" no longer hold.

v2.1 (task P20261115.000001/01-fix, minor, additive; no consumer breaks). Changes against v2.0:
- Frozen Lead allow-list: a Lead session already handed over may call the MCP tool `mcp__plugin_aico_lead-session__lead_new_session` and `SendFeedback` (exact name, case-sensitive); every other tool is still denied with `cap-lead-frozen`, `continue:false`. Only the Frozen branch changes; the first-freeze branch (clean point) still allows only the MCP tool.
- Guard record event `bg` (`{ v, at, ev: "bg", session: <sessionKey> }`): written by the host (`scripts/hook-host.mjs` → `hooks/lib/cap-effects.mjs#recordBackground`), not by the `cap.M1` rule, for each allowed Lead `PreToolUse` with `tool.background` true (`hook-event` v1.2), at every token level (not with `AICO_GUARDS=off`, see v2.2); never for a Step session or a denied call. Same append rules and line cap as the other rows. Read by the former lead-replace script (removed) (`lead-session-mcp` v2.1); the `cap` guard ignores it.

v2.0 (task P20261114.000001/01-feature, major, breaking, CEO approved at the Plan Gate 2026-11-14; ADR `docs/adr/0070-cap-in-handoff-mod.md`; shipped: the old guard script is deleted). The handoff mod: the cap becomes the `cap` guard (rule `cap.M1`) of the hook engine (`mod-hook` v1, `hook-event` v1, manifest `cap`, `mod-manifest` v1); the old guard script and its two `hooks/hooks.json` entries are removed. Changes against v1.2:
- Threshold `T` = the snapshot's `threshold` (`aico-settings` v3.0 `pipeline.context_cap`: default 180000, valid 60000-250000, invalid → 180000 with one warning per session naming the bad value). Freeze point `F` = floor(T x 0.9). Constants and both formulas live only in the cap rule module (hooks/rules/cap.mjs); `mods/lib/context-cap.mjs` and `scripts/run-cap.mjs` re-export or read from it; no other production file holds `180000` or `162000` (AC13).
- Bands, per session (the dispatch line `Context cap: <cap> handover <n>` carries `<cap>` = `T` and `<n>` = `F`):

  | Band | Step session | Lead session | Record |
  |---|---|---|---|
  | tokens < `F` | silent, every tool | silent, every tool | nothing |
  | `F` ≤ tokens < `T` (**freeze**) | v1.2 Step branch: only a `Write` of a new Handoff or of one new findings ledger in the run folder; every other tool denied with the v1.2 Step reason; SubagentStop blocks once without a Handoff | v1.2 Lead branch in order: Frozen (session already handed over) → deny all but the MCP tool and `SendFeedback` (v2.1), `continue:false`; Step running → deny `Agent`/`Task` with the wait reason, other tools pass; else clean point → `contextHandover`, first-freeze deny without `continue:false` | `deny`, `handoff`, `ledger` as v1.2; Lead `handover` event |
  | tokens ≥ `T` (**hand over**) | same as freeze (no further tool is allowed or refused) | as freeze, plus `continue:false` on every deny, so the turn ends; a Step running still writes no Lead Handoff | as freeze |

  At the first freeze deny of each agent (Step) or session (Lead) the engine adds one `systemMessage` for the CEO (`aico cap: …`, design file); it is a CEO note, never model text: the model learns only from the deny reason. Tests at T-1-F boundaries: 161999 silent, 162000 freeze, 179999 freeze, 180000 hand over, 180001 hand over (AC11), each for Step and Lead.
- Order: no active run → pass, whatever `tokens.state` (the guard is a run budget; a transcript read error outside a run never denies). In an active run: tokens `state: 'none'` (no usage row yet) count as 0; then the bands.
- Fail mode **closed** (was open), in an active run only: tokens `state: 'error'`, an invalid snapshot, a crash or a timeout → deny `cap.M1: <error word>` (Lead: no freeze, plain deny). The host supplies `run` when `state` is `error` (`hook-event` v1.1). A run error (`run` is `{ error: true, slug, folder }`: the run is found but its run record or run state cannot be read) at or over `F` → deny `cap.M1: unreadable`, naming the fix (repair or remove the malformed `lead-handover.jsonl` in the run folder, or check `run-state show`), in Step and Lead sessions, no effect and no guard record row; below `F` it passes like any call. A lookup that fails before a run is named reads as no active run.
- The off switch `AICO_CONTEXT_GUARD=off` is retired; `AICO_GUARDS=off` (engine, CEO only) replaces it for all guards, in the Lead session only; Step sessions are always guarded (`mod-hook` v1 engine step 1).
- The guard record is `.company/work/<slug>/guard.jsonl` (was `context-guard.jsonl`), same rules, plus the event `guards-off` (`{ v, at, ev: "guards-off", session: <sessionKey> }`, once per session). Every guard's denies, `cap.M1` included, also go to the engine's deny log (`mod-hook` v1 engine step 7), which the guard record does not replace.
- `subagent-stop` moves into the engine's `SubagentStop` entry, same behaviour.
- The 54000 fast path becomes floor(60000 x 0.9) from the cap module; the run is found as in v1.1.

Provider: `hooks/rules/cap.mjs` (rule `cap.M1`), run by `scripts/hook-host.mjs` through the `PreToolUse` and `SubagentStop` entries of `hooks/hooks.json`. Consumers: every Role and the Lead during an active run (they see only the refusals), `skills/handoff/SKILL.md`, `skills/pipeline/references/lead-handover.md` and (v2.1, `bg` rows only) the former lead-replace script (removed). Uses `hook-event` v1.4, `lead-handoff` v3.0, `run-state` v3.1 (`runCap`, read-only). History: v1.0 to v1.2 held the guard in a script of its own with the hand-over point frozen per run (ADR 0056, ADR 0069); both are superseded by ADR 0070.
