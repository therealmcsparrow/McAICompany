# Contract: skill-catalog v1

Provider: the module scripts/skill-catalog.mjs (read, validate, status; imports no `node:child_process`) and the baseline file deps/3rdpartyskills.json. Consumers: `install-skills.mjs`, `settings.mjs`, `settings-server.mjs`, `skill-picks.mjs`, `sbom.mjs`, `check.mjs`, the migration, add and record commands in scripts/role-skills.mjs. Rationale: ADR 0062.

## Layers
| Layer | Path | Writer | Holds |
|---|---|---|---|
| Baseline | deps/3rdpartyskills.json, located from `import.meta.url`, never from `CLAUDE_PLUGIN_ROOT` or the working folder | a plugin release | `categories`, `groups`, `entries`; read-only; repo-owned, so a command here is trusted as text only and is still never run |
| User | `<user home>/.mcsparrow/3rdpartyskills.json` | `/aico:add-skill`, migration, `role-skills record`, the installer's `hash` and `vetted` write | `entries` only |

- **User home** = `os.userInfo().homedir`, the operating system's answer. `os.homedir()` is not used: it reads `HOME` and `USERPROFILE`, which a repo's `.claude/settings.json` `env` can set. A throw → no user layer, one warning.
- **`MCSPARROW_HOME` set** and not resolving to `<user home>/.mcsparrow` → the user catalog and user-level selections are not read or written, one warning `role skills: MCSPARROW_HOME is set, the user catalog is not read`. The read path never moves.
- **Settings folder moved** by any env (`HOME` and `USERPROFILE` too, since `settings.mjs` follows `os.homedir()`): user-level selections are not counted, `--selected` user-scope installs from `<user home>` and takes no `gates.installs: auto` answer. Other settings and `/aico:setup` are unchanged.
- Nothing is read from a product folder: no catalog file, no project setting and no env value supplies an entry, a command or a path. A project selects by name only (`aico-settings`). One exception, migration: an old `.company/project.md` section line becomes a user entry only after a CEO form that shows its validated name, source, commit, license, `vetted` and `approved` per line. A value that fails its pattern is never shown and its line stays; a line's license must also pass the old section's pattern (`design-skills-section`). Migration keeps the old `approved` date: it only decides whether a research Step runs, never trust or install. A `## Skills` line that becomes a new entry gets its category from the same form: `role-skills migrate --apply` takes `--category <n>:<name>=<key>`, one key the preview printed for that line. A line that matches an entry in either layer keeps that entry's category (**Merge**, **One commit per name**), and a new entry from `## Design skills` is `design`.
- Tests pass `{ home }` to the exported functions. No env value is a seam.

## Schema (`"schema": 1`; unknown keys refused)
Baseline: `{ "schema": 1, "categories": {…}, "groups": {…}, "entries": […] }`. User: `{ "schema": 1, "entries": […] }`.
- `categories`: exactly the closed list `engineering`, `design`, `security`, `quality`, `product`, `research`, `content`, each to its Role ids: engineering: architect, senior-engineer, backend-engineer, frontend-engineer, desktop-engineer, game-engineer, ai-data-engineer, devops. design: ui-ux-designer, brand-artist, game-artist, motion-artist, prompt-artist, frontend-engineer, desktop-engineer, game-engineer. security: security, pentester, vuln-scanner. quality: qa, code-reviewer, fresh-reviewer, hands-on-tester, persona-tester, accessibility-tester. product: product-manager, account-manager, ux-researcher, legal, reprompter. research: market-researcher, tech-researcher, design-researcher, skill-researcher. content: writer, editor, marketer, localizer, support. `check.mjs` fails when an `agents/*.md` Role is in no category or a listed Role has no agent.
- `groups`: group name → ordered list of skill names or `{ "include": "<group>" }`. Only the baseline has groups; expansion order and de-duplication give the same `/aico:setup` commands as the old manifest.

| Entry field | Rule |
|---|---|
| `skillname` | `^[a-z0-9][a-z0-9-]{0,63}$`. Baseline may end in `*` (wildcard: shown, never selectable, reason `a wildcard names no one skill`). Plugin kind: `<p>:<skill>`, both parts that pattern |
| `skillcategory` | one closed-list key |
| source, exactly one of | `skillrepo` `^[A-Za-z0-9][A-Za-z0-9-]{0,38}/[A-Za-z0-9._-]{1,100}$`, repo part not `.` or `..`; `skillinstaller`; `skillplugin` `^[a-z0-9][a-z0-9-]{0,63}$`, equal to `<p>` |
| `skillinstaller` | at most 200 characters, tokens `^[A-Za-z0-9@._/:=+-]+$` joined by single spaces (so no shell operator or control character), and one token exactly `[@scope/]<pkg>@<x.y.z>` |
| `skillcommit` | `^[0-9a-f]{40}$`. Required on a user `skillrepo` entry; optional on a baseline one; refused on the other kinds |
| `license` | text of 1 to 64 characters after trimming, stored trimmed, with no control, format, separator or invisible character (`Cc`, `Cf`, `Zl`, `Zp`, every `Default_Ignorable_Code_Point`, U+180E, U+2065, tag characters U+E0000-U+E007F), so whitespace only counts as empty; any other text is accepted, with no check against a list or the repo. Required on every user entry, as the CEO states it; nothing checks it. Optional on a baseline entry, and never inferred or filled in. A pipe character is stored as typed; `--status` prints it as `%7C` |
| `vetted` | real date not after today. Optional. On a user entry: the installer writes it with `hash` after both clean scans ("Selected install") and clears both after a failed or errored scan, before or after the install, unless `clearBound` refuses (Exports); migration moves the old value; a researcher record writes none. A command entry is never scanned and shows as not vetted, even if the file holds a date |
| `hash` | `^[0-9a-f]{64}$`, written only by the installer, after the scan at the commit and the scan of the installed folder both passed. Cleared first, before the scan at the commit, whenever one is stored (so a failed write refuses the skill and nothing is scanned or installed), then again by a failed or errored scan on either side of the install, and by Move (**One commit per name**). `clearBound` can refuse (Exports); no scan runs while the row read holds a hash, so a failed scan leaves none on that row. A `hash` or `vetted` key on another row of the name can then stay; read never trusts that row. No other write and no command sets or clears it |

Baseline carries `license` as a sourced value only (the run's Step 17 table, read 2026-11-06), and `vetted` on the `research` group's entries, as the old manifest did. With no license value, under a CEO exception (agentsec.M-SEC6, `.company/standards.md`): `vercel-react-best-practices`, `vercel-composition-patterns`, `two-factor-authentication-best-practices`. `aico:ui-design`, aico's own plugin, is a baseline entry with no license, in no group, so it adds no `/aico:setup` command. A license adds nothing to and changes nothing in a command.

Bounds: user file a regular file (`lstat`, a link is refused), at most 256 KiB, at most 200 entries. A bad file → empty user layer, `ERROR user catalog: <file too large|link|bad JSON>`. A bad entry → `ERROR user catalog entry <n>: <field> <reason>`, its text never echoed; it cannot be selected and nothing from it installs. Baseline entries still work, except that `installed (name only)` then gives `dispatch: no` (`--status`). A bad baseline → `check.mjs` fails; at run time `ERROR baseline catalog`, exit 1.

**Merge:** on a name clash the baseline wins and the clash is reported, except a user entry with the same source and a `skillcommit`, which pins that baseline entry for Role skill installs only. `/aico:setup` groups read the baseline alone, so their commands never change with the user file. A pin holds its own license and vetted date, from the old line or the CEO's form, never the baseline's, and `skillStatus` shows those.

**One commit per name** in the user file, for `addUserEntry`, migration and `role-skills record`: an equal entry writes nothing; another commit is refused unless a CEO form chose Move (`{ moveCommit: true }`), which sets the commit and license and clears `hash` and `vetted`, keeps the category and every selection, and other products then read `folder not recognized` until reinstalled; another source is refused. In one migration the first line of a name decides: a later line that would write another commit, license or vetted date stays, with its reason.

## Exports
`userCatalogPath({ home })`, `readBaseline()`, `parseBaseline(text)`, `readCatalog({ home })` → `{ entries, errors, clashes, warnings }`, `validateEntry(entry, layer)`, `licenseAsTyped(raw)`, `expandGroups(baseline, groups)`, `eligibleRoles(entry, categories)`, `selectable(entry)`, `approvable(scan, hash)`, `boundedFolderHash(dir)`, `skillStatus(entry, { home, productRoot, scope })` → `{ status, place, license, vetted }`, `vettedText(entry, vetted)`, `itemsProven(rootDir, name, hash, { place })` → `{ present, ok }` (`place` `project` or `user`, absent counts as `project`), `linkedSegments(rootDir)` → its linked segments (Status) as `.claude`, `.claude/skills`, `.agents` or `.agents/skills`, a segment that is linked hiding the one under it, `addUserEntry(entry, { home, moveCommit })`, `setBoundHash(name, hash, vetted, { home })` (writes both or neither), `clearBound(name, { home })` (clears both from every row of that name, refuses no row for what it holds, so a file with a bad row before a good one of the same name keeps no pin; it adds no value, and writing stored rows back unchecked is the one exception to the rule that every write refuses a banned value, approved by the CEO. One refusal besides file-level errors: it finds the first row of the name that passes `validateEntry(row, 'user')` before and after the strip, none counting as a position, and when the two differ the strip would change which row is read, so it writes nothing and returns `ERROR user catalog entry <n>: clearing the pin would make this row the one read, nothing written; fix or remove it by hand`, `<n>` being the row the strip would put first, counted from 1, its text never echoed. While the two are equal the row read keeps its source and commit, so a clear cannot lose a pin). Writes are atomic (temp file, then rename) and keep every other entry's values.

## Selected install (`install-skills --selected`)
`--selected [--dry-run] [--skill=<name> ...]`. With `--skill`, only the named skills are handled. A name outside the selection or not matching `^[a-z0-9][a-z0-9-]{0,63}$` (so no plugin name) → `ERROR`, exit 1, nothing installed. `--dry-run` neither scans nor installs; it prints what would run.

| Kind | What happens |
|---|---|
| Repo with a commit (user entry or user pin) | No license → `no license`, nothing installed. Status already `installed` at the skill's `scope` → prints `installed <name> (<scope>)`, no scan, no install: a stored `hash` means both scans below passed. `scope` `project` and a linked segment under `<product root>` (Status) → `hash differs`, naming the segment, no scan, nothing installed, nothing stored, since the CLI could write through it and the files that load cannot be proven. Else, when the entry holds a `hash`, `clearBound` first (a failed clear logs its error and `scan failed: <name>, nothing installed, missing`, counts one failure, and scans and installs nothing; a dry run writes nothing). The hash sits on one user row that every product reads, so a scan or install that then fails turns another product's proven copy to `folder not recognized` until reinstalled, the same cost as Move. A clear refused here because it would change the row read (Exports) is such a failed clear: no scan runs, and the stored hash stays on the row read, which a folder that did not prove still does not match, so `--status` stays `dispatch: no`, and another product's proven copy stays `installed`. Then scan at the commit; failed, errored or not approvable → `clearBound`, nothing installed, the skill reported `missing`. `scope` `project` and a copy under `<user home>` that does not prove against the scan hash (`itemsProven` with place `user`) → `hash differs`, naming the home copy, nothing installed, nothing stored, since `skillStatus` reads both places and could never say `installed`. Folder at the skill's `scope` (Status), under `<user home>` only when `scope` is `user`, already equal to the scan hash → no install, on to the scan of the installed folder. Else install `#<commit>` once, at the skill's `scope`: `project` with no `-g`, working folder `<product root>`; `user` with `-g`, working folder `<user home>`, so a skill selected at user level by one Role and at project level by another installs only at user scope and both Roles read that one status; every child with `HOME` and `USERPROFILE` set to `<user home>` and `CLAUDE_CONFIG_DIR` removed in any letter case; compare every item (`itemsProven`) with the scan hash; different → `hash differs`, nothing stored, how to remove it printed, exit 1. Equal, installed or not → scan the installed folder before anything is stored (`scanInstalled` of `skillspector-scan` at the skill's `scope`, with `<product root>` and `<user home>` as this run has them). It passes only with at least one result, each `pass` or `findings` with `blocking: false`; a pass → `setBoundHash` with today, and no other path binds. Anything else, a refusal or a throw included → `clearBound`, `scan failed after install`, nothing stored, exit 1. `clearBound` refused after either failed scan → its error line, then the same `scan failed` or `scan failed after install` line and exit 1, with the file unchanged: the row read holds no hash by then, and a `vetted` date on it stays and reads `from the old list, not scanned here`. After `hash differs` or `scan failed after install` the folder stays until the CEO removes it, so the Lead shows the stop form (never auto), `--status` gives `dispatch: no` whatever the CEO answers, and the skill is on no `Role skills:` line. That holds while the pin row is read or a user layer error says it may not be (`--status`); a valid file with the pin row removed, by hand or by deleting the file, reads as no pin, and only the writer of that file can do that |
| Unpinned baseline repo | Never scanned or installed here; `needs a pin` naming `/aico:add-skill`, with `(installed, name only)` added when a folder of that name is there. Whether a Role may load it is the `--status` word, which depends on the place |
| Installer | `manual` line and warning only |
| Plugin | Only logs `plugin <name>: skipped, enable it with /plugin` |
| Wildcard | Cannot be selected, so never reached |

Output lines the Lead reads, per skill: `$ <cmd>`, `FAILED <cmd>: <error>`, `installed <name> (<scope>)` or `installed <name> (<scope>, vetted <YYYY-MM-DD>)`, `scan failed: <name>, nothing installed, missing`, `ERROR user catalog entry <n>: clearing the pin would make this row the one read, nothing written; fix or remove it by hand` (before the `scan failed` line it comes with), `scan failed after install: <name>, nothing stored, <what>. The folder stays until you remove it; <how>` (`<what>` is `verdict findings, blocking`, `verdict error <reason code>`, `refused: <refusal>` or `no usable result`, never the tool's free text), `hash differs: <name>, nothing stored. The folder stays until you remove it; <how>` (`<how>` for scope `user`: `run this from your home folder only: npx -y skills@1.7.4 remove <name> -g -a claude-code -y`; for scope `project`: `delete these folders by hand: <.agents folder> and <.claude folder>`, because a command run in the product folder would run a repo's own copy of the CLI), `hash differs: <name>, nothing stored. Your home folder holds another copy; run this from your home folder only: npx -y skills@1.7.4 remove <name> -g -a claude-code -y`, `hash differs: <name>, nothing stored. This is a link or not a folder; delete it by hand: <segment>` (one line per segment, one failure per skill), `no license: <name>, nothing installed`, `needs a pin: <name>, …`, `manual <cmd>` with its `WARNING:` line, `plugin <name>: skipped, …`, `not in the catalog: <name>`, `ERROR invalid catalog entry: <name>`. In a dry run: `[dry-run] scan <source> at <commit>, then:`, `[dry-run] <cmd>`, `[dry-run] working folder: <folder>`; a linked segment prints its `hash differs` line after `[dry-run] `, with no command, and counts as no failure. That line, `no license:` and `ERROR invalid catalog entry:` print no command in a dry run, so the Lead asks no Install question for them: it shows the line as is, the skill stays off, and `gates.installs` `auto` gives them no Install either. Last line `<done> installed, <failed> failed`; exit 1 when `<failed>` is above 0. `settings folder moved` comes first when it applies.

`install-skills --status` takes neither `--dry-run` nor `--skill` (`ERROR`, exit 1). One line per selected skill: `<name> | roles: <roles> | <status> | place: <place or -> | license: <text> | <vetted text> | dispatch: <word>`, the texts as in Status, with a pipe character in the license text printed as `%7C`, so free text adds no field before `dispatch:`. A selected name the catalog lacks or cannot select reads `not in the catalog`, with `dispatch: no`. The word holds the "Error cases" rule: `yes` for status `installed`, or `installed (name only)` with place `user`; `session list` for a plugin entry, kept only when the session's skill list holds it; `no` for anything else, including `installed (name only)` with place `project`, even when `<user home>` holds a folder of that name too, since the product root is checked first. `installed (name only)` with place `user` is `no` too when this read of the catalog gave any error or warning (a bad file, a bad row of any name, `MCSPARROW_HOME` set, an unknown home): a pin may be what was lost, so a folder a scan refused must not turn loadable, and a row damaged in its name cannot be tied to a skill. The status text stays; a proven `installed` keeps `yes`. After the selected lines comes one line per selectable catalog entry no Role selects: `roles: -`, read at project scope, `dispatch: no`. It gets no question and its word is never read.

## Status (`skillStatus`; only `lstat`, `realpath`, `readdir` and file reads)
No child process, no parsing of `skillinstaller`, no network, and no file content is read through a link: `realpath`, `lstat` and `readdir` give only where a link leads and which names are there.

A **linked segment** is a link, a junction, a non-folder or a path `lstat` cannot read at `.claude`, `.claude/skills`, `.agents` or `.agents/skills` under a root; not found means `ENOENT` or `ENOTDIR`, any other error cannot read. Under `<product root>`, which a clone can fill: a `<name>` reached through it (`lstat`, an error other than not found counts as there), of any file type, is a present item that never proves, so a repo entry with a commit reads `folder not recognized` and any other non-plugin entry `installed (name only)` at place `project`; and `--selected` installs nothing at that root, whether or not `<name>` is there. Under `<user home>`, which a clone cannot fill and a dotfile manager may link: the segment and everything under it are skipped and `--selected` is not refused. A `<product root>` that is the home folder still counts as `<product root>`.

Place checked: `<product root>` first, then `<user home>`, under `.claude/skills/<name>` and `.agents/skills/<name>`. With `scope` `user` only `<user home>` is checked: a folder or link under `<product root>` does not count, whatever its hash, so with nothing in `<user home>` a repo entry with a commit reads `missing` and an installer or unpinned baseline repo entry reads `not found`. `scope` is `user` when any Role selecting the skill has a user-level list, else `project`. Plugin entries are not read here.
- Repo entry with commit: `installed` = every item present at every place checked proves. An item proves when it is a real folder (`lstat`) whose `boundedFolderHash` equals `hash`, or a link (the CLI's `.claude/skills/<name>` usually is one) whose `realpath` equals the `realpath` of `.agents/skills/<name>` at the same root, itself a real folder that proves. A dangling link or a link loop does not prove. `folder not recognized` = an item is present that does not prove: the hash differs, none is bound, a link that leads elsewhere, or over the bound. `place` names the first place holding such an item, else the first place holding any. `missing` = nothing there. `--selected` treats `folder not recognized` like `missing`, except for a linked segment or a home copy that does not prove ("Selected install").
- Installer or unpinned baseline repo entry: `installed (name only)` = a folder or link of that name, version not checked; `not found` = none, which is not proof, since an installer may write elsewhere. The status text is the same at both places; a folder or link in the product root can come from a clone, so only place `user` gives `dispatch: yes`, and only when the catalog read gave no error or warning (`--status`).
- Plugin entry: `checked at run start`.
- Every skill also shows two texts, as plain text and never as markup, on the settings page, in `--status` and in the run-start form. License: `<license>, as stated, not checked`, or `no license on record` for a baseline entry with none, which never blocks selecting, installing or printing it. Vetted: `vetted <YYYY-MM-DD>` when a date is recorded, else `not vetted`. A date on a user entry with no `hash` reads `vetted <YYYY-MM-DD>, from the old list, not scanned here`; among user entries only migration leaves that state. An installer entry always reads `not vetted`, so `skillStatus` returns `vetted` null for it even if the file holds a date.
- `boundedFolderHash`: the same files, order and bytes as `skillFolderHash` of `skillspector-scan` (a test holds them equal); refuses a link at the top, at most 2000 files and 64 MiB, over → null.

## Error cases
A stored selection outside the catalog or the Role's categories: `aico-settings` `ignored` by field path, never its value, and never dispatched. Any stop before Save in `/aico:add-skill` writes nothing. `role-skills record` writes a new repo or plugin entry. On a new entry with no license stated it writes nothing for it and prints `no license stated: <name>`. A command entry no list holds, or a source other than the list's → `ERROR entry: <reason>`, nothing written. A user catalog that cannot be written → `ERROR user catalog: cannot write`, nothing changed. Free text reaches `role-skills add` and `role-skills record` only as one line of JSON on stdin, never on a command line. A selected skill reaches a `Role skills:` line only with status `installed`, with `installed (name only)` at place `user` and a catalog read with no error or warning, or as a plugin entry in the session's skill list at run start; otherwise it is left off and the run records `degraded: missing <name>`. `installed (name only)` at place `project` also gets a run-start form, never auto, that names the place and says aico will not tell a Role to load that folder; no answer puts the name on a line.
