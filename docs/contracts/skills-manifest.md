# Contract: skills-manifest v2.5

Provider: `deps/skills.json` (plugin groups, user scope) `.company/project.md` `## Design skills` (group `design`, project scope, see `design-skills-section` v1.1) and `## Skills` (group `skills`, project scope, see `skills-section` v1). Consumer: `scripts/install-skills.mjs`, called by `aico:setup`, `aico:research`, `aico:feature`, and the Lead's skill picks (`skill-recommendation` v1).
v1 = 0.8.1 shape. v2 is additive: every v1 manifest is valid v2. v2.1 is additive with `skills-section` v1: group `skills` and `parseSkillsSection`; every v2 manifest is valid v2.1. Fix round 1 (task skill-researcher-scan, unreleased, additive): a project line with `commit` installs that commit. v2.2 drops `mattpocock-skills` as a plugin dependency; no required plugin skill is left in the research presence check. v2.3 is additive: `retiredSkills`, `--retired` and `--remove`, and the writing clean-up skill leaves `core`. v2.4 is not additive: every pinned skills CLI `add` runs from an aico-owned fetch with node on the bin file and a cleaned PATH (no npx), v2.5 changes it again, not additive: a manifest command (impeccable, now pinned `npx -y impeccable@4.8.0 skills install`) is printed as `manual <cmd>` plus a `WARNING:` line at any scope and never run.

## Group entries
- `{ "name", "source" }` → `npx -y skills@1.7.4 add <source> -s <name> -g -a claude-code -y` (user scope; the CLI pin is one constant, bumped in a change of its own, agentsec.S1).
- `{ "name", "install" }` → the literal install command (unchanged).
- `{ "include": "<group>" }` → new: expands to that group's entries. `core` contains `{ "include": "research" }`, so `/aico:setup` (default `core`) also installs `research`.
- Optional on any entry: `"license"` (SPDX), `"vetted"` (YYYY-MM-DD), `"commit"` (the SHA read when vetting, agentsec.S2). `license` and `vetted` are **required** on every entry of the `research` group (checked by `scripts/check.mjs`). A `deps/skills.json` `commit` is a record only and does not change the command.
- Commands from `deps/skills.json` are repo-owned. `name` and `source` of every entry still match the agentsec.M-SEC7 patterns (`name` may end in `*`); `check.mjs` reports any that do not.

## CLI additions to `install-skills.mjs`
| Flag | Effect |
|---|---|
| `--dry-run` | unchanged: `[dry-run] <cmd>` per missing skill, or `All skills already installed.`; group `design` lines read `[dry-run] (in <product root>) <cmd>` |
| `--missing` | prints `missing <name>` per missing skill (no commands), exit 0; nothing missing → no output |
| `--project <path>` | adds group `design` parsed from that file's `## Design skills` and group `skills` parsed from its `## Skills`. `<path>` must end in `.company/project.md`; product root = its grandparent. Groups `design` and `skills` without `--project` are `unknown group design` / `unknown group skills` |
| `--retired` | one `retired <name>` line per retired name installed in `~/.claude/skills`; none → no output; exit 0 |
| `--remove <name>` | removes one retired installed skill with the pinned skills CLI (see Retired skills below) |

- Groups `design` and `skills` repo entries → the printed command is `npx -y skills@1.7.4 add <source> -s <name> -a claude-code -y` (**no `-g`**), run with `cwd` = product root. **With a `commit` on the line, `<source>` is `<owner>/<repo>#<commit>`** (the skills CLI 1.7.4 reads `#<ref>` as the ref and clones a 40-hex ref at that sha; `parseFragmentRef`, `cloneRepo` → `cloneAtSha`). Command entries → the manifest's `install` string. Plugin entries and names containing `:` are skipped.
- Run form (v2.4), for every pinned skills CLI `add` command, user and project scope (`--remove` is the exception, see Retired skills): nothing from a product folder steers or runs. `npm-cli.js` beside `process.execPath` (missing → `FAILED`) is run by `process.execPath` with `install --prefix <home>/.mcsparrow/cli/skills-<version> --ignore-scripts --save-exact skills@<pin>`, working folder = that aico folder. Then `process.execPath` runs the package's `bin` file by absolute path, no shell, `cwd` = product root (project) or home (user), with a PATH of absolute entries only, none inside the product root and no `node_modules/.bin` of the product root or a parent, plus `NoDefaultCurrentDirectoryInExePath=1`. A package that is not the pinned version or whose bin file is missing → `FAILED <cmd>: skills@1.7.4 bin file is missing`. Proven by tests with a root `.npmrc` `prefix=` and a planted `npx-cli.js`, `node_modules/.bin/node.cmd`, `git.exe`, POSIX `node` and `git`, and a `.bin` in a parent folder; each failed on the previous `npx --prefix` form. Run on Windows only: the POSIX programs were planted but not run on a POSIX host. Not proven: other files a repo could hold that the CLI reads from its working folder. A manifest `install` string (for example `npx -y impeccable@4.8.0 skills install`) is never run (v2.5), at user or project scope, and not counted as failed: `main` prints `manual <cmd>`, then `WARNING: <name> is a third-party installer that aico has not inspected, so it was not run. To install it, run it yourself: <cmd>`, and exits 0 when nothing else failed. The WARNING line is wrapped in ANSI yellow (`ESC[33m` ... `ESC[0m`) when stdout is a TTY and `NO_COLOR` is unset, else plain; `env.color` overrides it in tests. Claude Code strips colour from tool output, so setup tells the Lead to show the line as a visibly marked warning. The manifest string must be version-pinned. Setup says so in its consent text. User-scope pinned CLI installs filter only `node_modules/.bin` folders from PATH (other folders under home stay), since there is no product folder.
- The printed command string is built only from allow-listed tokens. Pinned skills CLI `add` commands run as `execFile(process.execPath, [bin, ...args])`, no shell on any platform; `--remove` still runs its `npx` string as in Retired skills. The remaining shell form (`--remove` and `installExec`) runs only when the home path matches `^[A-Za-z0-9 _.:\/()@+-]+$` and does not end in a backslash, else `FAILED ... cannot be used`; never an `args` array with `shell: true` (node.M-SEC5, DEP0190).
- Installed detection adds `<product root>/.claude/skills` and `<product root>/.agents/skills` when `--project` is given.
- Exports for tests: `plan`, `runAll`, `expand(manifest, groups)`, `missing(manifest, groups, installed)`, `parseDesignSkills(markdown, manifest)` and `parseSkillsSection(markdown, manifest)` (the manifest is needed for the byte-identical command check). Parsed repo entries carry `commit` when the line has one.

## Retired skills (v2.3)
- Export `retiredSkills(manifest, releasesDir)`: names from `bom-ref` `skill:<name>@…` in every `releases/*/sbom.cdx.json`, minus names the current manifest matches (wildcards included), sorted. An SBOM is untrusted: a link, a file over 2 MiB or bad JSON is skipped, and a name that does not fully match `^[a-z0-9][a-z0-9-]{0,63}$` (so no `*`) is dropped, because it reaches a command string.
- Installed means a folder or link of that name in the `~/.claude/skills` listing; nothing is followed or read.
- `--remove <name>` checks in order: the name fully matches that pattern and is a current `--retired` line, else `ERROR not a retired installed skill`, exit 1. `--dry-run` prints `[dry-run] npx -y skills@1.7.4 remove <name> -g -a claude-code -y` only, exit 0.
- Without `--dry-run`, on Windows (the one platform proven to run it without a prompt) the command runs as one string; the folder or link gone → `removed <name>`, exit 0. The command failed or the entry is still there → `FAILED <cmd>: <error>`, exit 1. On any other platform nothing runs and it prints `manual <cmd>`, exit 0.
- Output is captured: stdin ignored, stdout and stderr piped and held, never inherited; the script prints exactly one line of its own. `<error>` is the first non-empty captured stderr line, else the exit code, control characters replaced by spaces, at most 200 characters.
- `--remove` runs from the home folder, never the product folder (a repo's `node_modules` or `.npmrc` must not steer `npx`), and stops after 120 s with `FAILED <cmd>: timed out, it may still finish`, exit 1; on Windows the timeout ends only `cmd.exe`, so the removal can still complete. User-scope installs also run from the home folder and stop after 10 min (`FAILED <cmd>: timed out, it may still finish`).
- Every skills CLI child (install and remove) gets `DO_NOT_TRACK=1` and `DISABLE_TELEMETRY=1` (`skillsEnv`). Read in `skills@1.7.4` `dist/cli.mjs`: `isEnabled` (:2808-2810) gates `track` (:2833, `/tele/t`, the only call on the remove path, :7424) and `fetchAuditData` (:2814-2815, `/tele/audit`, called :5467). Not gated: `isRepoPrivate` (:80-82, `api.github.com/repos/<owner>/<repo>`, called :5340); the blob path for `BLOB_ALLOWED_OWNERS` and `BLOB_ALLOWED_REPOS` (:5086-5095; `fetchTreeBranch` :3839-3842, `fetchSkillMdContent` :4054, `fetchSkillDownload` :4062-4067, whose repo `zapier/connectors` downloads from `connectors-skills.zapier.com`, :3832, :4066); on a GitHub rate limit or auth failure `fetchRepoTree` (:3934-3951) sends `GITHUB_TOKEN` or `GH_TOKEN` as a Bearer token (:3779-3781, :3847) and then runs `gh api` with the user's login (:3890); the GitHub host comes from `GH_HOST` (:32-36); a `-g` install of a source that took no blob path also requests `api.github.com/repos/<owner>/<repo>/git/trees` (:5728-5730); a failed blob install falls back to a clone (:5110); and the clone from github.com (:240). A pin bump re-reads these lines.
- `--retired` or `--remove` with a group, `--missing`, `--project` or the other of the two → `ERROR`, exit 1. `--dry-run` is accepted with either.
- Setup removes a retired skill only after the CEO's explicit pick; with nobody to pick, nothing is removed.

## Presence check (AC8), run by the Playbook at run start
1. `node install-skills.mjs <groups> [--project .company/project.md] --dry-run`. No command printed → present.
2. Plugin skills the run wants (`anthropic-skills:deep-research`, plugin design skills) → checked against the session's skill list; missing required plugin skill → its `/plugin install <plugin>` line is shown with the commands; optional ones are not shown.
3. Anything missing → show the printed commands, the destination lines of setup step 2 (telemetry off with no audit lines; api.github.com owner and repo check; the blob downloads for vercel, vercel-labs, heygen-com, remotion-dev from www.skills.sh/api/download, api.github.com and raw.githubusercontent.com; zapier/connectors from connectors-skills.zapier.com; a clone from github.com otherwise and after a failed download; the api.github.com tree request for `-g` installs; the `GITHUB_TOKEN`, `GH_TOKEN` or `gh` login use after a rate limit or auth failure; the npm registry) and the run form (npm into `~/.mcsparrow/cli`, node on the bin file, no npx, FAILED if the file is missing), and ask **one** form: Install (Recommended) / Skip. Install → same command without `--dry-run`, then tell the CEO to `/reload-plugins`. Skip → continue on the baseline, record `degraded: missing <name>, <name>` in the report/Handoff frontmatter. Never install without the form. No Role or Playbook runs `npx skills find`.

## Error cases
- `include` of an unknown group or an include cycle → throws `unknown group <g>` / `include cycle <a> -> <b>`, exit 1, nothing installed.
- `--project` path not ending in `.company/project.md` → `ERROR --project must point to <root>/.company/project.md`, exit 1.
- `--project` file missing or no `## Design skills` / `## Skills` section → that group is empty (not an error).
- A `## Design skills` line that fails `design-skills-section` v1.1 → `ERROR design skill line <n>: <field> <reason>`, exit 1, nothing installed in any group.
- A `## Skills` line that fails `skills-section` v1 → `ERROR skills line <n>: <field> <reason>`, exit 1, nothing installed in any group. `plugin <p>` sources are not allowed in group `skills`; at most 5 lines per area and 15 in all.
- A pinned install whose clone at the sha fails → the skills CLI exits non-zero; `install-skills.mjs` reports `FAILED <cmd>` as for any failure and never retries without the pin.
