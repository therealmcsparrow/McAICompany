# Contract: mod-hook v1

New Contract (task P20261114.000001/01-feature; the brief calls it `aico.mod-hook` v1). What a rule may answer and how the one engine runs the rule table. Provider: the hook engine, scripts/hook-host.mjs with the rule table hooks/rules.json and the pins hooks/pins.json (created by the build), wired in `hooks/hooks.json`. Consumers: every rule module under hooks/rules/, the hook check script, `context-guard` v2.0 (the `cap` guard), the savers. Uses `hook-event` v1, `mod-manifest` v1, `aico-settings` v3.0. Rationale: `docs/adr/0071-guards-as-rule-table.md`, `docs/adr/0072-guards-before-release.md`.

## Rule function
`rule(event, snapshot) → verdict`, pure: no `fs`, `net`, `http`, `child_process`, `process`, `fetch` or dynamic `import`, and no read of the environment (AC21; the check scans each rule module and the shared path module). The scan is a block-list over pinned, reviewed code: hygiene that catches mistakes, not a security boundary (the pins are). Input is the frozen `hook-event` v1 object and the frozen snapshot below.
Verdict (allow-list): `{ v: 'allow' }`, `{ v: 'deny', rule: '<rule ID>', message: '<1-300 printable chars>' }` or `{ v: 'note', rule: '<rule ID>', message: '…' }`. A deny or allow of rule `cap.M1` only may also carry `effect`: one of `cap-step-record`, `cap-lead-freeze`, `cap-lead-frozen`, `cap-warn`; the engine (pinned engine code, hooks/lib/cap-effects.mjs) then does the record writes and output shapes of `context-guard` v2.0. A rule never writes. Anything else (another key, another value, a changed event object, a thrown error, a promise) is invalid: a guard's invalid verdict is a deny `<rule ID>: invalid verdict`, a saver's is ignored (AC3). A rule never rewrites a payload: the engine never emits `updatedInput`.

## Rule table (hooks/rules.json, one row per rule ID)
`{ "event": "PreToolUse", "matcher": ["Bash","PowerShell"], "rule": "git-add.M-SEC1", "module": "git-add.mjs", "export": "judge", "fail": "closed", "timeoutMs": 300, "message": "aico guard git-add.M-SEC1: stage files by name" }`. `matcher` is a list of tool names or `["*"]`; `module` a file name in hooks/rules/; `fail` `closed|open`. Loaded only from the plugin root; a row whose rule ID has no manifest, or whose `fail` differs from its manifest, is unused (`mod-manifest` v1).

## Engine, per hook call
1. `env.guardsOff` and `event.session` is `lead` → no guard runs; savers run as usual. Once per session per active run, append `guards-off` to the guard record (`context-guard` v2.0) (AC16). In a `step` session `env.guardsOff` is ignored: Steps are always guarded, even when launched from a Lead with the switch on (CEO, Plan Gate). Only the CEO sets it, at launch; no tool call can reach the hook process environment.
2. Pins: hooks/pins.json holds one SHA-256 per file of the pinned set: scripts/hook-host.mjs, every `hooks/lib/*.mjs`, every `hooks/rules/*.mjs`, every `hooks/manifests/*.json`, hooks/rules.json, hooks/hooks.json, hooks/schema/hook-fields.json, company/model-floor.json. Pinned too, the dependency graph: hooks/lib/dep-hashes.mjs holds one SHA-256 per file reached by the static and literal dynamic imports of the scripts the engine loads (scripts/lead-handover.mjs, scripts/run-state.mjs; a branch ends at a hooks/lib or hooks/rules file). Once the pinned set matches, the host checks the graph (hooks/lib/dep-pins.mjs `verifyDeps`); hooks/lib/cap-effects.mjs checks it again before each import. A hash off, a pinned file missing (a deleted manifest included), an extra file in those folders, a file outside the plugin root, or a dependency changed, missing or newly imported → nothing loaded; every guard event denies `pins-mismatch`; the CEO is told at session start, naming the file (AC19). `AICO_GUARDS=off` still lets a `lead` event through (step 1). `node scripts/hook-pins.mjs write` rewrites both hash sets.
3. Snapshot (below) unreadable or invalid → guards deny `snapshot-invalid`; savers pass (AC17).
4. `event.drift` non-empty → guards deny `hook-payload-changed`; savers pass (AC18).
5. Guards first, in table order, then savers (Lead session only: a saver row never runs when `event.session` is `step`, AC28). The first guard deny wins; notes are collected.
6. Rules run in one `worker_threads` Worker per call (hooks/lib/rule-runner.mjs), never in the main thread. The main thread holds each row's `timeoutMs` (at most 1000) and the 3500 ms call deadline and calls `worker.terminate()` when one expires, so a synchronous endless loop times out too. A guard that throws, times out, or whose module is missing or unreadable → deny `<rule ID>: <error word>` (`crash`, `timeout`, `missing`, `unreadable`). A saver in the same case passes the call unchanged: the guard verdict and the notes collected so far stand (AC9).
7. Deny log: the engine (hooks/lib/deny-log.mjs; a rule never writes) appends each guard deny and guard failure to `<snapshot folder>/<root12>/denies.jsonl`: `{ "v": 1, "at", "rule", "kind": "deny"|<error word>, "session": <sessionKey>, "agent": <agentKey|null> }`, at most 1000 lines (the oldest third dropped on overflow), never a path, command or model text. The first row of a rule per `sessionKey` adds a CEO toast (`systemMessage`, design file). Read-only reader: `hook-check.mjs denies --session <sessionKey> --json` (newest 5). Write failure → the verdict stands, unlogged.

## Output to Claude Code
- Deny: stdout `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"aico guard <rule ID>: <message>"}}`, exit 0. The `cap` guard may add `continue`, `stopReason` and `systemMessage` as in `context-guard` v2.0.
- Deny on `SubagentStop` (the `cap` guard's once-only block): stdout `{"decision":"block","reason":<reason>}`, exit 0; a `stop_hook_active` stop always passes.
- Note: `systemMessage` only (the CEO's screen); never `additionalContext`, so a saver adds no model tokens.
- Allow: no output, exit 0.
- `hooks/hooks.json` timeout for engine entries: 10 s, so the engine's own 3500 ms deadline always answers first. The PreToolUse entry sets `onFailure: "block"` (cch.M-SEC3, Claude Code 2.1.295+), so a host kill, crash or invalid output blocks the tool. On SubagentStop `onFailure` has no effect: a kill lets the stop through (see Limits).

## Snapshot (Q-15)
The engine writes the resolved settings it needs (`threshold`, saver switches, `version` of `aico-settings`) under `<MCSPARROW_HOME or ~/.mcsparrow>/hook-snapshots/` (the snapshot folder): `<root12>/lead.json` at Lead `SessionStart` and at every `SubagentStart` (the Lead's next Step dispatch), and `steps/step-<agentKey>.json` at the first `SubagentStart` of that `agentKey` only (cch.M15: a later `SubagentStart` for the same agent, a resume or a teammate message, keeps the file). `root12` = first 12 hex of SHA-256 of the real project root: the real path of the nearest ancestor of the session cwd holding a `.company` folder, else the real cwd. Step files are not per root, because a worktree Step's cwd is not the Lead's. Written atomically (temp file, then rename), at most 4 KiB, `{ "v": 1, "at", "threshold", "savers": { "<id>": bool }, "floor": { "<role>": "haiku|sonnet|opus" }, "drift": bool, "settingsWarnings": [..] }` (`floor` from `company/model-floor.json`; unreadable → snapshot invalid). A Step reads its own file, else its root's `lead.json`; a missing, partial or invalid file is `snapshot-invalid`. At most 200 Step files; the oldest are deleted. So a settings edit applies at the next Step dispatch, never mid-Step (AC17).

## Fixtures
Per rule ID a folder hooks/fixtures/<rule ID>/ with synthetic JSON events built from the schema file (never a real payload): at least one `pass-*.json` and one `block-*.json` for a guard; plus `crash`, `timeout`, `malformed` and `missing-module` cases run by the engine harness for every guard. A guard missing a pass or a block fixture fails the check and does not ship (AC4).

## Session start
At Lead `SessionStart` the engine runs every fixture against the loaded table and compares the event to the schema file. Any failure: one `systemMessage` to the CEO naming the rule IDs or fields, the snapshot records `drift: true`, savers are off for the session, guards deny `hook-payload-changed` (AC18). Budget: at most 2 s at session start.

## Latency budget
One engine process per hook call, never one per rule. PreToolUse with a transcript read (last 1 MiB): p95 at most 250 ms on win32, measured by the engine task on the CEO's machine and recorded in its Handoff; a run over it is a Nit for release 1, not a block.

## Limits (not enforceable)
- A host kill lets the action through only where `onFailure` has no effect (SubagentStop, and Claude Code before 2.1.295); PreToolUse blocks (Output). The spike task measures what the host does.
- Plugin enabled mid-session (no `SessionStart` seen): no `lead.json`, so every guarded call denies `snapshot-invalid` until the session restarts or the next `SubagentStart` writes it.
- Self-protect is hygiene against a compliant model, not a sandbox. It judges `raw`, `expanded` and `real` paths, inline interpreters naming a settings word, and a directory change plus a write to a protected base name. Not caught: a path built from a variable set earlier in the same command, string concatenation or encoding inside a shell, a script written to a file and then run, a build tool or package script that writes on the agent's behalf, an archive extracted onto a protected path. Pins (step 2) catch a changed engine file at the next call; settings and snapshot edits are not pinned.
- Guards stop an agent, not a person: the CEO's off switch, a hand edit of the installed plugin or of `~/.claude/settings.json` outside a session are CEO acts.
- The plugin is the installed copy under `CLAUDE_PLUGIN_ROOT`. Developing aico with the plugin loaded from the source tree would put the source under self-protect; load the installed copy.

## Minimum CLI versions (ccmod.M8)
- Engine and mods as a whole: Claude Code 2.1.310 (the `aico-mods` minimum). The spike checked the eight events of `hooks/schema/hook-fields.json` on 2.1.325 (`03-prototype-backend-engineer.md`).
- `onFailure` on a hook entry: 2.1.295 (cch.M-SEC3); before it a host kill lets a PreToolUse action through.
- `CLAUDE_CODE_SUBAGENT_MODEL` and its `_FORCE` form, read by `model-floor`: 2.1.251 (`scripts/settings.mjs` `modelEnvLine`).
- Every other event and field of `hooks/schema/hook-fields.json` (`agent_id`, `agent_type`, `agent_transcript_path`, `tool_input.*`) is used on the 2.1.310 floor; no later tie is documented. A tie found later is added here and the schema file, never inferred in a rule. `hooks/pins.json` holds hashes only (`{ v, files }`), so a version note never lives there.

## Compatibility
New Contract, v1. A new verdict kind or a change in the engine order is a major; a new rule row or a new error word is a minor.
