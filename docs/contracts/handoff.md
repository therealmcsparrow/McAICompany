# Contract: handoff v2.2

Provider: every Role, through `aico:handoff` (Core, `skills/handoff/SKILL.md`). Validator: `scripts/handoff-lint.mjs`. Consumers: the Lead (`aico:pipeline`), later Steps, reviewers.
v1.0 = the Handoff shape in `skills/handoff/SKILL.md` at 0.10.0 (frontmatter, By line, `## Did`, `## Decisions`, `## Blocking`, `## Nits`, `## Next`, optional `## Standards`, `## Debt`). v1.1 is additive: a Handoff without the v1.1 parts is a valid v1.0 Handoff, and a reader that does not know v1.1 reads the frontmatter and body as before. v1.2 is additive too (part 4): a v1.1 Handoff, name byline included, still lints. v2.0 (part 5) is **breaking** (task elephant-goldfish): v1.2 shipped alone in 0.20.0, so the part 5 rules ship as v2.0 in 0.21.0 and no v1.3 was ever released. Part 5 adds the fresh reviewer, evidence for contests, escalation with CEO rulings, slugged exceptions bound to the run start, `--exceptions-for`, `--applied`, the `model:` key and the product-manager sections. What breaks for a v1.2 producer is in `## Migration from v1.2`.
Fix round 4 (still unshipped, so no version change): the v1.1 rules for pilot Roles live in `skills/handoff/references/pilot.md`, which only pilot Roles load; `skills/handoff/SKILL.md` keeps one pointer to it, so non-pilot Roles stop paying for pilot text. The findings ledger is written only when a handover is near (part 3).
Fix round 6 (CEO, after T15d `67-ai-data-engineer.md`; still unshipped): the pilot is a setting, `pipeline.review_format` (`aico-settings` v1.1), default `plain`, because T15d measured the pilot reviewer at +9.6% spend (n = 6 per arm, 2.6 SE). A Role is a pilot Role only when its dispatch carries `Review format: pilot` (`dispatch-prompt` v4.0). The ledger exists only for `status: handover` (part 3), prose under `## Blocking`/`## Nits` never starts with an ID (part 2), and no field holds a `|`.

v2.1 (task T15, minor, additive): `<slug>` in a Handoff path, in `--contests`, `--applied`, `--exceptions-for` and in an `## Exceptions` line is a work folder name as `work-folder-name` v1 defines it: a new name (`YYYY-MM-DD HH.MM - <Topic>`, spaces inside) or a legacy slug. Frontmatter `task:` is a work folder name or a plan task id (`^[A-Z][0-9]{1,3}[a-z]?$`, `T15`); another value is `ERROR line <n>: task must be a work folder name or a task id`. The run part of an exception line is read up to the first `/` (at most 120 characters), must pass `isWorkFolder`, and must equal the run folder name byte for byte, no case folding; exception keys (`<NN>-<role>:R-<n>`) and ADR slugs keep their patterns. A forged, case-changed or look-alike run part is no exception. A Role that writes a v2.0 Handoff behaves as before; a legacy slug keeps working.

v2.2 (task T7, minor): a work folder path is spelled exactly as on disk, on every file system (`work-folder-name` v1.1, `exactWorkPath`). A Handoff path, a `--contests` or `--applied` run folder, or an `--exceptions-for` slug whose `.company`, `work`, run folder or file part is listed only in another ASCII letter case prints `ERROR wrong letter case` and reads nothing (exit 1; exit 2 for `--exceptions-for`, as for a bad slug). A part that is not listed at all keeps its old error (`ERROR cannot read file`). `--exceptions-for` counts only lines whose run part equals the slug byte for byte. The case fold of the real-path read rule is gone: the real path must equal the lexical path exactly. The `.git`, `.env*` and device-name folds of the evidence path rule stay. A Role that writes a v2.1 Handoff behaves as before.

## v1.1 part 1: the top block
A fenced block with info string `aico-top`, directly after the `By:` line and before `## Did`. Exactly these seven keys, in this order, one `key: value` line each, no other lines:

| Key | Value |
|---|---|
| `status` | `done \| blocked \| needs-ceo \| handover`; must equal the frontmatter `status` |
| `files` | `[path, …]`; same set as frontmatter `files-touched` (`[]` when that is absent) |
| `ac_ids` | `[AC1, …]`; same set as frontmatter `acceptance-ids` (`[]` when absent) |
| `rule_ids` | `[proj.M3, …]` rule IDs this Step applied or checked; each matches `^[a-z][a-z0-9-]{0,30}\.(M\|S\|Y)(-SEC)?\d{1,3}$`; `[]` allowed |
| `risks` | `[R-1, …]` finding IDs (part 2) that carry a risk, or `[]` |
| `read_next` | `[path, path#heading, R-2, …]` at most 5 pointers the next Step should read; pointers, never copied text; `path#heading` keeps the heading text as written (spaces allowed after `#`, no commas); `path` and `R-n` have no spaces |
| `tokens_used` | integer (the Role's own count, if it has one) or `unknown`; the token ledger (`token-ledger` v1) is the authoritative count |

- The frontmatter stays the routing source. The block repeats `status`, `files` and `ac_ids` so a reader can stop after it; a mismatch is malformed.
- **Malformed** = missing or extra key, wrong order, bad value, a mismatch with the frontmatter, a line over 1000 characters, or a second `aico-top` block. A malformed block **blocks the Step**: the Lead re-dispatches the same Step with the lint errors; it does not consume a Fix round.
- **Pilot scope (CEO, Brief Gate Q5; Fix round 6):** the block is **required** for `code-reviewer` Handoffs and for `senior-engineer` compliance-pass Handoffs **whose dispatch carried `Review format: pilot`**; the Lead then runs `handoff-lint.mjs <file> --require-top`. Without that line (the default, `pipeline.review_format: plain`) those Roles write a v1.0 Handoff and the Lead runs the plain lint. Every other Role may omit the block; when present it is validated. Widening to all Roles is a later minor bump after the AC26 numbers.

## v1.1 part 2: finding rows
Pilot Roles write each finding in `## Blocking` and `## Nits` as one row:
- Blocking: `- [contract|spec|security|test] <ID> | <file>[:<line>[-<line>]] | <problem> | <why> | <fix>`
- Nit: `- <ID> | <file>[:<line>] | <problem> | <why> | <fix>`
- `<ID>`: `R-<n>` (code review), `C-<n>` (compliance pass), `T-<n>` (tool check confirmed from `rule-check` v1). IDs are **stable**: a Fix round keeps the ID of a finding it re-reports and never reuses an ID for a different finding. Builders cite IDs in `## Did` (`fixed R-2`), never copy the text.
- `why` is never empty: a rule ID plus a few words, or a plain reason.
- **No `|` inside a field** (Fix round 6): the lint splits on every `|`, so a quoted row or a shell pipe in the problem text breaks the row. Rephrase, or name the character in words.
- **Every bullet under `## Blocking` and `## Nits` is a row** (Fix round 6). Prose never starts with an ID (T15d: "R-11 to R-17 … are still open" under `## Nits` failed 4 of 6 lints); a summary of open findings goes in `## Did` or `## Next`, or into `risks`/`read_next`.
- Plain English (no rows) stays for the body prose, Gate summaries, Must exception requests, `## Debt` and security risks; the `security` Role stays outside the pilot.
- Plain format (no `Review format: pilot`): findings follow the v1.0 shape `- [tag] <file:line> — problem — fix`. `T-` rows passed in by the pre-filter keep their `rule-check` v1 row shape and are linted as rows when row-shaped.

## v1.1 part 3: the findings ledger
A pilot reviewer writes `.company/work/<slug>/<NN>-<role>.findings.md` **only for `status: handover`**, so a handover mid-review loses nothing (AC23):
```markdown
---
step: 07
role: code-reviewer
base-commit: <sha>
---
## Checked
- scripts/x.mjs
## Findings
- R-1 | open | [spec] | scripts/x.mjs:12 | <problem> | <why> | <fix>
```
- **When (Fix round 6, replaces Fix round 4's "near a handover").** At the first of: its context passes 75% of the `Context cap:` handover point `<n>` (that is 60% of `<cap>`; with no or a malformed `Context cap:`, 90000 tokens), or it can't tell and has read more than 15 files, the Role decides whether it will finish. If it will not, it starts the ledger, keeps it up to date and returns `status: handover`. It also continues an existing ledger of the same review chain (a handover link or a Fix-round reviewer after one): once a chain has a ledger, every later link appends to it. A Handoff that ends `done`, `blocked` or `needs-ceo` has no ledger beside it (same `NN`). Reason: T15b measured an always-written ledger as part of a +16% spend on a re-review that never handed over (`48-ai-data-engineer.md`), and T15d saw a ledger on 2 of 6 `done` re-reviews.
- **Guarantee.** A pilot Handoff with `status: handover` always has its ledger next to it, holding every finding so far and every checked file. `handoff-lint.mjs <file> --require-top` checks it (Validator).
- Status: `open | fixed | withdrawn`. Rows are appended or have their status changed, never deleted. A handover link and a Fix-round reviewer continue the same file (same IDs). `## Checked` lists every file already reviewed.
- Tag: one of the four Blocking tags (part 2), or `[nit]` for a Nit (`- R-3 | open | [nit] | scripts/x.mjs:3 | <problem> | <why> | <fix>`). The Nit's Handoff row (part 2) drops the tag. No `|` inside a field (part 2).
- The final Handoff's rows are the `open` ledger rows when a ledger exists; the Lead commits the ledger with the Step when it exists.
- **IDs without a ledger.** A Fix-round reviewer with no ledger in its chain keeps the IDs of the rows it re-reports from the earlier reviewer Handoffs of the task, lists closed ones in `## Did` (`fixed R-2`, `withdrawn R-5`), and numbers a new finding from 1 + the highest `R-<n>` (or `C-<n>`) in any earlier Handoff or ledger of the task, so no ID is reused.
A continuation appends every new finding to the chain's ledger before it writes its Handoff.

## v1.2 part 4: Role id bylines, contested findings, contracts
- **Byline.** New Handoffs write `By: <role id>` (the bare Role id, as in `role:`). A v1.1 byline `By: <Name> (<role>)` stays valid; a Role never gets a name (`role-names` v1.3).
- **Reviewer rows carry an ID.** Under a bare Role id byline, every `## Blocking` row of `code-reviewer`, `security`, `pentester` and `vuln-scanner`, and every tagged Nit row, has `R-<n>` (`C-` and `T-` rows pass) after the tag: `- [tag] R-<n> <file:line> — problem — fix` (pilot rows keep part 2). A `[open-decision]` Nit needs none. IDs are stable across Fix rounds (part 2).
- **Key.** A finding is named `<NN>-<role>:R-<n>`, taken from the file name `.company/work/<slug>/<NN>-<role>.md` of the Handoff that holds the row, so `05-code-reviewer:R-2` and `06-security:R-2` never share a key. **Lineage:** rows with the same `<role>` and `R-<n>` in Handoffs of one run folder are one finding; its key is the one with the lowest `NN`. A collision between parallel Steps of one Role only makes the lint stricter; it never closes a finding.
- **Contest** (builder). `## Contested` lines, counted only in a Handoff whose `NN` is above the `NN` of the cited key and whose Role is neither the raising Role nor a reviewer Role. One contest per lineage per run; a second is a lint error. The line shapes are in part 5 (v2.0: a contest needs evidence or is an escalation).
- **Answer** (reviewer). `## Contests` lines `- <NN>-<role>:R-<n> accepted — <reason>` or `… rejected — <reason>`, counted only in a Handoff of the Role that raised the finding with an `NN` above the contest's. Any other answer is a lint error and is ignored.
- **States.** `open`, `contested` (blocking until answered), `accepted` (closed), `rejected` (blocking), plus `fixed` (a later Handoff of the raising Role, in a later round, `status: done`, no longer lists the row under `## Blocking`; a Handoff that carries an answer to it is never that fix) and `excepted`. States come only from the lint output, never from Handoff prose.
- **Security findings never close by contest.** `accepted` is refused (lint error; the finding stays `contested` and blocking) when any row of the lineage was ever tagged `[security]`, or cites a pack security rule (`<prefix>.M-SEC<n>`, also `S-SEC` and `Y-SEC`) or `proj.M1` to `proj.M4`, or the raising Role is `security`, `pentester` or `vuln-scanner`. It closes only by a fix or by a CEO exception: a line `- <slug>/<NN>-<role>:R-<n> — <scope> — <reason> — approved: <YYYY-MM-DD> (CEO)` under `## Exceptions` of `.company/standards.md` (the `aico:ruleset` shape), `<slug>` being the run folder name and the rest the lineage key. It counts only in that run and only as part 5 says (run slug, run start); a line without a slug counts for nothing and lint prints `warning: exception <key> names no run; not applied`. The Lead writes it from the CEO's own Ship Gate answer. No Handoff text counts (`## Contests`, `## Decisions`, "CEO approved").
- **`contracts:`** frontmatter `contracts: [<contract> v<x>[.<y>], …]`, **required** under a bare Role id byline (a v1.1 name byline needs none; `[]` is allowed): missing → `ERROR frontmatter: missing contracts …`. The name-drift test scans every Handoff that has the key or a Role id byline. Each item is checked by the `contract-index` v1 cite rule: the Contract is in the index, the major equals the current major and the minor is not newer. Else `ERROR frontmatter: contracts …`.
- Old terms: the ledger statuses `open | fixed | withdrawn` (part 3) are ledger rows only; the contest states above are a separate table.

## v2.0 part 5: fresh reviewer, evidence, escalation, rulings
- **Real-path read rule.** Every file the lint reads on behalf of Handoff text (contest evidence, `rulings.md`, `standards.md`) is read only when the real path (`realpathSync.native`) of its lexical path equals that path exactly (v2.2: no case folding on any platform) and lies inside `realpath(root)`, `lstat` shows a regular file with one hard link, and the `fstat` of the opened handle is that file. A miss refuses that read and never falls back to the lexical path (CWE-59). Size caps apply before reading. Root = `<run folder>/../../..`; a run folder not shaped `.company/work/<slug>` has no root, so no evidence can be checked and no exception or ruling is read.
- **Tag** `[comprehension]`: only on a `fresh-reviewer` Blocking row; from any other Role → `ERROR line <n>: comprehension tag is for fresh-reviewer only` (in the single-file lint and in `--contests`, where the tag then does not make a finding uncontestable). The fix goes to the doc's author (plan → architect) and is a text change only.
- **Fresh-reviewer Handoff.** `fresh-reviewer` is a reviewer Role (cannot contest; rows need `R-<n>`). Frontmatter `review-mode: plan | code`, required for that Role (`ERROR frontmatter: missing review-mode`), refused for every other Role (`ERROR line <n>: review-mode key is for fresh-reviewer only`). The first two `##` headings are `## Paraphrase` (200-1200 characters, counting its non-empty lines trimmed and joined by one line break) then `## First pass` (every line `- R-<n> …` or `- none`). From the `By:` line to the end of `## First pass` no token may match a run file name `\d{2,3}-[a-z][a-z0-9-]{0,40}\.md` that is not a plan name (`plan-tasks` v1: `03-plan.md`, `architect-plan.md`) → `ERROR line <n>: Handoff cited before the first pass ends`.
- **Lineage.** For `fresh-reviewer`, lineage = role + `review-mode` + `R-<n>`, so plan-mode and code-mode `R-1` are two findings; `fixed` and an answer need the same mode too. The key stays `<NN>-<role>:R-<n>` with the lowest `NN`.
- **Contest.** `- <key> — <reason> — evidence: <ref>[; <ref>]` (1-3 refs; reason 1-500 characters). Ref = `<path>[:<n>[-<n>]]` or `<path>#<test name>` (name 1-120 characters, no control character, `#` or `;`). Path: the `plan-tasks` v1 path rule (no absolute path, `..`, glob, `.git`, `.env*`, folder), then the real-path read rule, a regular file of at most 1 MiB; a line range must lie inside the file and a `#` name must occur in it. A contest that fails any of it, or has no `evidence:`, → `ERROR <file> line <n>: contest of <key> has no checkable evidence`, and it does not count as the lineage's contest. At most 100 evidence files are read per `--contests` call. A line that does not start with a finding key keeps the shape error.
- **Escalate.** `- <key> — escalate — <reason>` (reason 20-500 characters) counts as the lineage's one contest. The finding is `escalated` (blocking): the raising Role cannot answer it (`ERROR … is escalated; only a CEO ruling closes it`). A contest or escalate of a lineage with any `[comprehension]` row → `ERROR …: comprehension finding <key> cannot be contested; change the text`.
- **Rulings.** `.company/work/<slug>/rulings.md` (real-path read rule, at most 64 KiB), `## Rulings` lines outside code fences `- <key> — upheld|overruled — <reason> — ruled: <YYYY-MM-DD> (CEO)`; the last line for a key counts; counted only for an `escalated` lineage. `overruled` on a security lineage (part 4) → `ERROR rulings.md line <n>: ruling on security finding <key> is refused; …`, ignored, still `escalated`. A ruling file that is not read (link, hard link, over the cap, unreadable) → one warning line and no rulings. Only the Lead writes it, from the CEO's own Gate answer; the Lead shows every applied ruling verbatim at the next Gate under `rulings on file: confirm each is yours` (`skills/pipeline/references/contest.md`).
- **States** add `escalated` (blocking), `upheld` (blocking; a further contest is the second contest, an error) and `overruled` (closed). `fixed` still closes a lineage. Output order: `ERROR`, `warning`, `state`, `unresolved`, `escalated <key>`, `ruled <key> upheld|overruled`, `excepted`.
- **Exceptions** (replaces the part 4 counting rule): `- <slug>/<NN>-<role>:R-<n> — <scope> — <reason> — approved: <YYYY-MM-DD> (CEO)`, read with the real-path read rule (missing → none, no warning; refused → the existing warning). Counted only when the run folder's name and the line's run part both pass `isWorkFolder` (v2.1) and are equal byte for byte (no case folding), and `approved:` is on or after the UTC date of `run-state` v1.5 `show(root, <slug>).started` (the latest `start`, so a reused slug does not inherit an old exception). No record, an unreadable record or no `start` → no exception applies and one `warning: run <slug> has no start; no exceptions applied` (only when a line for this run exists). An unslugged v1.2 line → `warning: exception <key> names no run; not applied`.
- **`--exceptions-for <slug>`**: `node handoff-lint.mjs --exceptions-for <slug>` (cwd = product root; slug checked first, a bad slug → `ERROR slug must be a work folder name`, exit 2) prints `exceptions on file: <k>`, the number of `## Exceptions` lines naming `<slug>/` with a real date of any age, exit 0 (no `standards.md` → 0); exit 1 when `standards.md` exists but cannot be read. The Lead uses it to tell the CEO about earlier exceptions of a reused slug.
- **`model:`** frontmatter: required on a `fresh-reviewer` Handoff with `review-mode: code`, value `opus | sonnet | haiku | fable` (the model on its dispatch `Settings:` line); refused on every other Handoff → `ERROR line <n>: model key is for fresh-reviewer code mode only`. A value ranked below the code-reviewer floor in `company/model-floor.json` (`haiku` < `sonnet` < `opus`, `fable` unranked; file unreadable → `opus`) → `warning line <n>: model <m> below the code-reviewer floor` (the command line prints it before the routing JSON; exit unchanged). The key is self-declared, never proof of the dispatched model.
- **Research inputs.** For each earlier research report a Role used (the dispatch's `Research inputs:` line), `## Sources` holds `[S<n>] <path> — report <YYYY-MM-DD|undated> — research-report`; such a line without a real date or `undated` → `ERROR line <n>: research report source needs its date`. A `## Blocking` row or `## Decisions` line whose every `[S#]` cite is a `research-report` source must end with `(unverified)`, else `ERROR line <n>: claim rests only on an earlier research report; re-check it or mark (unverified)`; one cite to another source, or a line with no cite, passes. No `## Sources` section → the rule does not apply.
- **Product-manager sections**, before `## Next`: `## Glossary` (`- <term> — <definition>`, term 1-60 characters, definition 10-300), `## ADR drafts` (`- <slug> — <decision 10-200> — why: <reason 10-300>`, slug `^[a-z0-9][a-z0-9-]{0,50}$`), `## Prototype question` (exactly one line of 10-200 characters). Another line shape → `ERROR line <n>: <section> line shape`; on any other Role → `ERROR line <n>: <section> is for product-manager only`.
- **Starting rule 6** (`skills/handoff/SKILL.md`) gains: a `Worktree: <path>` line → change files only under that path, run git only as `git -C <path>`, never read or change the main tree's working files; the `Files:` fence and every other rule 6 limit apply inside the worktree. Use absolute paths only, never `cd` or `Set-Location` into the worktree, and never `git stash` (the stash list is shared by all worktrees).
- **Export** `parseLocations(text)` from `scripts/handoff-lint.mjs`: every `<path>[:<n>[-<n>]][,<n>[-<n>]…]` in the location part (before the first ` — `, or the second field of a `|` row; at most 8192 characters), plus a bare `:<n>[-<n>]` that binds to the path before it → `[{ path, from, to }]` (`from` and `to` are null for a whole file; a single line has `from` = `to`). `CHANGELOG.md:10-13, documentation/concepts.md:72,78` gives three entries, `scripts/check.mjs:106 and :808-809` two. Anchored, linear patterns. `contests(runFolder)` also returns `lineages`: `{ key, role, mode, n, state, holders: [{ file, nn, round, tag, text }] }` per finding, in key order, for `review-loop` and `plan-review`.

- **`--applied <run folder>`** (v2.0, read-only, changes no state; `--contests` output and exit code stay as above): the run folder is checked as for `--contests`; a folder not shaped `.company/work/<slug>`, a bad slug or bad usage → the usage line, exit 2. Prints `rulings on file: confirm each is yours (<k>)`, then one line per applied ruling in file order (the `## Rulings` line that counts for an escalated lineage: the last line per key, not an `overruled` security finding), then `exceptions on file for <slug>: confirm each is yours (<j>)`, then one line per `## Exceptions` line of `standards.md` that passes the run-scope checks above (slug equal to the run folder name, `approved:` on or after the latest `start`), whether or not it matches a lineage yet. Each listed line is `> ` plus the line as read, without its line end; Cc, Cf, Zl and Zp characters print as `\u{<hex>}`; a line over 1000 characters is cut there and followed by `> … (<n> more characters)`. The `warning: run <slug> has no start …` and `warning: exception <key> names no run …` lines follow the lists. Both files are read by the real-path read rule; a file that exists but cannot be read → `ERROR cannot read rulings.md` or `ERROR cannot read standards.md`, exit 1, no list; a missing file counts 0. Exit 0 otherwise. The Lead pastes the output into the Gate summary unchanged (`skills/pipeline/references/contest.md`).

## Validator (`scripts/handoff-lint.mjs`)
- `node handoff-lint.mjs --contests <run folder>` (v1.2): reads every `<NN>-<role>.md` of the folder (regular files of at most 64 KiB, at most 500 entries; a file over the cap, a non-plain file or a line over 1000 characters is skipped with a `warning:` line). Prints `ERROR <reason>` lines, `warning: …` lines, one `state <key> <state>` line per finding, then `unresolved <key>` for each `contested` finding (the Ship Gate list) and `excepted <key>` for each exception (the Ship Gate summary). Exit 1 on any `ERROR`, 2 on bad usage, else 0. It reads `.company/standards.md` of the run's root by the real-path read rule (part 5): a regular file of at most 256 KiB; missing → no exceptions; a link, another type, over the cap or unreadable → no exceptions and one warning line. Only lines of its `## Exceptions` section outside code fences count; a bad date, a missing `(CEO)` mark, a `<slug>` other than the run folder name or a date before the run's latest start counts for nothing (part 5). v1.3 adds the `escalated` and `ruled` lines and the `rulings.md` read.
- `node handoff-lint.mjs <handoff.md> [--require-top]`: exit 0 and the routing JSON on stdout (v1.1 adds `"top": {…} | null` and `"findings": [IDs]`); exit 1 and `ERROR <reason>` lines otherwise. The lint does not read settings: the Lead passes `--require-top` only for a dispatch that carried `Review format: pilot`.
- With `--require-top` and frontmatter `status: handover` (Fix round 4): the sibling ledger `<NN>-<role>.findings.md` (same folder, same `NN` and `role` as the Handoff's file name) must exist and pass `--findings`, and every finding ID in the Handoff's rows must be in it; else `ERROR handover without findings ledger` or `ERROR finding <ID> missing from ledger`. A Handoff file name that does not match `^\d{2,3}-[a-z][a-z0-9-]{0,40}\.md$` → `ERROR cannot locate ledger`. The Lead treats this like a malformed top block: same Step re-dispatched with the errors, no Fix round.
- `node handoff-lint.mjs --findings <ledger.md>`: validates a findings ledger.
- **Hints (Fix round 6, additive to the error text; exit codes unchanged).** A row with more fields than its shape (Handoff row 5, ledger row 7) ends its error with `; a | inside a field splits it, write it without |`. In row mode, a `## Blocking`/`## Nits` bullet with 1 field ends its error with `; every bullet here is a finding row, put prose in ## Did or ## Next`.
- Input is LLM-written: size cap 64 KiB, anchored linear patterns, no `eval`, no YAML library (proj.M1 to M4). The ledger path is built from the checked file name only, inside the Handoff's folder; a symlink there → `ERROR cannot locate ledger`.

## Error cases
- No `aico-top` block, Role outside the pilot (or a pilot Role dispatched without `Review format: pilot`) → valid (v1.0 behaviour).
- No `aico-top` block with `--require-top` → `ERROR missing aico-top block`.
- Row without `why`, or a Blocking row without a tag → `ERROR line <n>: …`.
- Unknown ID prefix → `ERROR line <n>: finding ID must be R-, C- or T-<n>`.
- Pilot Handoff `status: done` with no ledger → valid (Fix round 4).

## Migration from v1.2
What breaks for a v1.2 producer:
1. A `## Contested` line without `— evidence:` that is not an escalation → `ERROR <file> line <n>: contest of <key> has no checkable evidence`. It does not count as the lineage's one contest, so the finding stays Blocking.
2. An `## Exceptions` line in `.company/standards.md` that names no run → not applied, one warning. A slugged line dated before the run's latest `start` → not applied.
3. A Handoff whose `contracts:` names `handoff` v1.x → the `contracts:` cite ERROR (another major).

What changes for a v1.2 reader: `--contests` adds `escalated` and `ruled` lines after `unresolved`, and `lint` and the command line print `warning` lines; a line reader skips lines it does not know.

How to move: Roles write `contracts: [handoff v2.1]` (`skills/handoff/SKILL.md`). A run started on 0.20.x and resumed on 0.21.0 keeps its earlier Handoffs: `--contests` reads their contest lines, never their `contracts:` key, so a contest in them without evidence shows that ERROR and the builder contests again with evidence, or escalates, in its next Handoff. To keep an exception, the CEO rewrites it as `- <slug>/<NN>-<role>:R-<n> — <scope> — <reason> — approved: <YYYY-MM-DD> (CEO)` for the run it is for, dated on or after that run's latest `start`; `handoff-lint --exceptions-for <slug>` counts the lines on file. The Lead never edits `.company/standards.md`.
