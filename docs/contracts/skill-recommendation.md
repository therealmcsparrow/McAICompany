# Contract: skill-recommendation v2.0

v2.0 (task role-skills-file, major, per `docs/adr/0007-contract-minor-versions.md`; rationale ADR 0062): `vet` prints `entry` in place of `record`, holding no `license` or `vetted`, plus `stated_license` for the form to show. `role-skills record` takes each new entry's license from the CEO's form and writes no `vetted`; there is no `no-license` reject code. `design-researcher` Handoffs go through `lint` and `vet` too. Approved picks go into the user catalog and Role selections (`skill-catalog` v1, `aico-settings` v1.12), not into `## Design skills` or `## Skills`. Role skill installs no longer use `check-install`; the post-install scan runs inside `install-skills --selected`, before it stores anything, and the stop form reads that command's output.

v1.3 (task skill-audit-bugs, minor, per `docs/adr/0007-contract-minor-versions.md`): the cited contracts moved to `design-skills-section` v1.2, `skills-section` v1.1 and `skills-manifest` v3.0. The old unpinned `impeccable` line is accepted on a `skills` group line too, as the same known old form. Nothing in a recommendation line changes.

v1.2 (task input-fix, T10; additive): `lint` and `vet` check the exact letter case of the work folder and Handoff file in `<handoff>` with `exactWorkPath` of `work-folder-name` v1.1, before the link checks. Another letter case → `refused: wrong letter case`, exit 2. A Handoff missing in every case keeps `refused: handoff not found`.

Provider: the `skill-researcher` and `design-researcher` Roles (`agents/skill-researcher.md`, `agents/design-researcher.md`), in their Handoffs. Lint and gating scan: `scripts/skill-picks.mjs`. Consumers: the Lead (`skills/lead/references/skill-picks.md`: the approve form, the license questions, the record, the Install / Skip form, the post-install checks), the CEO.
Uses: `skillspector-scan` v1 (`vetCandidate`), `design-skills-section` v2.0 (field allow-list), `skill-catalog` v1 (entry, record, `--selected`), `research-report` v2.0 "Researcher Handoff extension" (`fetches`, `depth`, `## Findings`, `## Sources`).
Still v1 and unreleased. **Fix round 1 (CEO decision 1, security B3, ADR 0019):** the Role no longer scans. The scan that gates the forms is run by the Lead through `skill-picks.mjs vet`, a deterministic tool, on the exact commit the Role vetted; the install pins that commit; a bad post-install scan stops the run. **Fix round 2 (ADR 0020):** the verdict is bound to the installed bytes. `vet` scans only the folder the skills CLI will install, only for a commit on a branch or tag of the named repo, and records that folder's hash; after install, `check-install` compares it with `skills-lock.json`. Command-source picks are no longer approvable, because aico cannot pin what their command fetches.

## Input
- The dispatch carries the line `Area: stack | product-type | company-type | design`, written in the Goal block. Absent or another value → the Role writes `status: blocked` with `missing area` under `## Blocking` and recommends nothing.
- `design` also reads `## Personas` and `## Art direction`; every area reads `stack`, `product_type` and the current catalog and selections. `company-type` reads `audience` and `goal`.
- Before the dispatch the Lead runs `skillspector.mjs detect --json`; `installed: false` → the AC10 install form first; Skip → no dispatch, the Gate summary says "no skill picks without the scanner" (AC3).

## Handoff (on top of `aico:handoff` and the researcher extension)
- Frontmatter adds `area: <area>`. (`scan-mode` is gone: the Role runs no scan.)
- Sections, in this order, headings exactly: `## Candidates`, `## Recommended set`, `## Rejected`, then the usual `## Findings`, `## Sources`. Lists only (proj.S2, Persona P3).
- `## Candidates`, one line each: `- <name> — source <source> — license <id> — last commit <YYYY-MM-DD> — installs/stars <as found> — key <y|n> — vetted <y|n> — fit <high|medium|low> — <recommended|rejected>`. Installs and stars are shown as found, never used to rank.
- Every candidate is in `## Recommended set` or in `## Rejected` (AC1).
- When a skill has both a repo source and a command source, the Role recommends the repo source (only a repo source can be approved).

## Recommended line (`## Recommended set`, at most 5, ranked by fit, then vetting evidence)
```
- area: <area>; name: <name>; source: <source>; license: <license>; vetted: <YYYY-MM-DD>; commit: <commit>; why: <why>; approved: pending
```
The whole line matches `^- area: (stack|product-type|company-type|design); name: ([^;]+); source: ([^;]+); license: ([^;]+); vetted: ([^;]+); commit: ([^;]+); why: ([^;]+); approved: pending$` (anchored, no nested quantifiers), each line ≤ 500 characters, then each field:
| Field | Allowed |
|---|---|
| `name`, `source`, `license`, `vetted`, `why` | exactly the `design-skills-section` v2.0 field allow-list, with one parser for both. So `license: -` passes only on a plugin line; a repo or command line with `-` fails the lint (`field: license`), since `aico:sourcing` rejects a candidate with no license. |
| `commit` | repo source: `^[0-9a-f]{40}$`, the commit whose files the Role read (from the GitHub page or the keyless API, agentsec.S2); command or plugin source: `-` |

## Rejected line
`- <name> — <code>: <one line, no backtick, no ;>`. Role codes: `license`, `api-key`, `stale` (no commit in 12 months), `no-fit`, `fork`, `not-vetted-in-budget`, `instructions-in-files` (noted, never followed, agentsec.M-SEC1), `too-large`. Scan codes are the Lead's, shown in its approve form:
- `scan-findings`: critical/high, or blocking.
- `scan-error`: verdict `error`, with its reason.
- `commit-not-in-repo`: the commit is on no branch or tag of the named repo (for example a fork's commit served under the upstream name).
- `scan-not-possible`: a command source (cannot be pinned), the skill not in the repo at that commit, the skill not bound to one folder (root `SKILL.md`, name differs from folder, same name twice, unreadable name), a link or submodule in the repo, or the fetch refused.

## `scripts/skill-picks.mjs` (Node built-ins, cwd = product repo; refusals `refused: <reason>` on **stdout**, exit 2, like `skillspector-scan`)
| Command | stdout (exit 0) |
|---|---|
| `lint <handoff>` | `{ "v":1, "area", "lines":[{ "n", "ok", "field"?, "reason"? }], "picks":[{ "n", "kind":"repo\|command\|plugin", "name", "source", "commit", "entry", "stated_license" }] }`. One `picks` entry per passing line. `entry` is the `skill-catalog` v1 entry the record writes after approval: name, source, commit and default category (design → `design`; stack and product-type → `engineering`; company-type → `product`), holding no `license` or `vetted`. `stated_license` is the line's license, shown in the form as what the researcher stated, never stored by itself. `n` is the line number; offending text is never echoed. |
| `vet <handoff> --json` | runs `lint`, then scans each pick, then prints `{ "v":1, "area", "mode", "lines":[…as lint], "picks":[{ …as lint, "scan": <skillspector-scan results[] entry> \| null, "scan_refused": <reason> \| null, "hash": <64 hex> \| null, "approvable": bool, "reject_code": <code> \| null }] }`. Progress lines go to stderr (`vet: <i>/<k> <name> <verdict>`). |
| `check-install --name <n> --hash <h> --json` (Fix round 2; not used by Role skill installs since v2.0, whose `-g` install has no lock file in the working folder) | `{ "v":1, "name", "bound": bool, "reason": null \| "no-lock" \| "no-entry" \| "hash-mismatch" }`. `<n>` = the skill name allow-list, `<h>` = `^[0-9a-f]{64}$`, both taken from `vet` output; else `refused: usage …`. Reads `<cwd>/skills-lock.json` only: `lstat` a regular file ≤ 1 MiB that parses as a JSON object with an object `skills` → else `no-lock`; `Object.hasOwn(skills, <n>)` with an object entry whose `computedHash` is a string → else `no-entry`; `computedHash === <h>` → `bound: true`, else `hash-mismatch`. Nothing from the file is echoed. |

- `<handoff>` must match `.company/work/<work folder>/<NN>-(skill|design)-researcher.md` (`<NN>` two digits; the path is split at its slashes and the folder passes `isWorkFolder` of `work-folder-name` v1, a new name or a legacy slug; at most 300 characters; v1.1 is additive) and be a regular file ≤ 256 KiB. More than 5 lines → lines 6+ fail with `too many entries`.
- **Scan per pick in `vet`** (mode from settings; `vet` never passes `--mode`):
  - repo: `vetCandidate({ source, commit, name })` (`skillspector-scan` v1): reachability, fetch at that commit into a quarantine, the link check, the bound folder, its hash, the scan of that one folder, clean. One fetch per distinct `(source, commit)`. `hash` = the returned `hash`.
  - command: not scanned. `scan: null`, `hash: null`, `scan_refused: "command source cannot be pinned"`, `approvable: false`, `reject_code: scan-not-possible`. (A name match against an installed copy proves nothing about what the command fetches, proj.M-SEC3.)
  - plugin: not scanned, never installed by the Lead; `scan: null`, `hash: null`, `approvable: true`, shown as "plugin skill, not scanned; installed only by you with /plugin". A plugin pick no list holds is a new entry like a repo pick: it gets its license question and `record` writes it.
- `approvable` (repo) = `scan.verdict` is `pass`, or `findings` with `blocking: false`, `counts.critical === 0` and `counts.high === 0` (AC2), **and** `hash` is set. Otherwise `reject_code`: `scan-findings` (findings), `scan-error` (error), `commit-not-in-repo` (refusal `commit not in repo`), `scan-not-possible` (any other refusal). No license is no reject code: on a line that passed the lint the CEO states the license. `static-fallback` is allowed and shown as "static fallback, not an LLM scan". A skill with `refs_not_bundled > 0` is allowed; the form says so.
- `refused: skillspector missing` (exit 3) or `refused: git missing` (exit 2) → nothing is approvable; the Lead offers the AC10 form or says git is needed.
- The `## Recommended set` line `- (none: no candidate passed vetting)` (Error cases) is accepted by the lint as an empty set, byte for byte; any other text there is a lint line.

## The Lead's side (`skill-picks.md`)
1. `vet` the Handoff (the path from the dispatch, never typed from Role text). A failing lint line is dropped and named by number, never repaired. Commands use tokens from `vet` output only.
2. **Approve form** (never auto): the approvable picks, each with the Lead's scan in words (`no-llm scan of commit abc1234, 0 critical, 0 high, 1 medium`), and the not-approvable ones with their `reject_code` and reason. Approve the set (Recommended) / Change / Skip. Skip writes nothing. The CEO may change the default category and picks the Roles.
3. **License questions**, one per new entry (repo or plugin pick), showing `stated_license` as stated and not checked, always with `No license, skip this skill` and `Cancel`. A `stated_license` of `-` states none and is not offered as an answer. Cancel writes nothing for any pick, since the record runs only after every question.
4. **Record:** `role-skills record` with one line of JSON on stdin, in a quoted heredoc, never on a command line (`skill-catalog` v1). It writes each new entry with the CEO's license and no `vetted`, and sets `approved` to today on the selections it records, even unchanged. A new entry with no license stated writes nothing and prints `no license stated: <name>`.
5. **Install / Skip form**: the exact commands from `install-skills --selected --dry-run`, which install the recorded commit (`skill-catalog` v1). Install means `install-skills --selected` with one `--skill=<name>` per Install pick; with no Install pick nothing runs. The form also says that `npx skills update` would move a skill off the scanned commit. Nothing installs unless the approve form says yes and the Install form says yes; only a user-level `gates.installs: auto` (`aico-settings` v1.12 lock) answers the Install form, and only while `get` prints `settings_folder_moved` false (absent counts as true), never the approve form (AC5). `approved` never answers either form (agentsec.M-SEC4, proj.M-SEC8).
6. **Post-install checks**, for each approved repo pick that got Install (`gates.installs: auto` answers Install), after the install command ran (whatever its exit code). A pick that got Skip has no install line and no checks and records `degraded: missing <name>`. The Lead runs no scan here and reads the `install-skills --selected` output for that skill: before storing anything the installer has compared every item with the scan hash at the skill's scope and scanned the installed folder (`skill-catalog` v1 "Selected install").
   Go on only when the skill's line is `installed <name> (<scope>` with no `FAILED`, `hash differs`, `scan failed` or `missing` for it. That skill's own lines decide, since the exit is 1 for every pick when one fails. **Every other outcome stops the run** (fail closed): any of those lines, or no `installed` line for that skill. The stop is a CEO form (never auto, whatever the Gate settings): the skill, what failed (for a `hash differs` line that says `The folder stays`: "the installed files are not the files aico scanned before you approved", then the line; for any other `hash differs` line: the line alone, since nothing was installed; for `scan failed after install`: the `<what>` that line prints; else the line, or "the check gave no usable result"), and how to remove it: what the installer printed, else the same text by scope. Scope user: `npx -y skills@1.7.4 remove <name> -g -a claude-code -y`, run from the home folder only, since a `-g` removal needs no product folder and a repo's own copy of the package runs otherwise. Scope project: delete `.agents/skills/<name>` and `.claude/skills/<name>` under the product root by hand; the form shows no command, since one run in the product folder would run that repo's copy. Options: Stop the run (Recommended) / Keep it and go on. The Lead runs no removal command (AC14); Keep is recorded in the Gate summary with what failed. Neither answer changes the record: on these outcomes the installer stored no hash, and a failed scan cleared `hash` and `vetted`, so `--status` gives `dispatch: no`, the skill stays off every `Role skills:` line, and a later Install scans again.

## Error cases
- The Lead's `detect` says not installed → the AC10 form before any dispatch (AC3); the Role never checks the tool.
- No candidate passes the Role's vetting → `## Recommended set` holds the single line `- (none: no candidate passed vetting)`.
- No pick is approvable after `vet` → no approve form; the Gate summary lists each pick with its `reject_code`.
- A line that fails the lint, an over-long line or a sixth line → dropped, its number in the Gate summary.
- An install with `hash differs` or `scan failed after install` → the stop form of The Lead's side 6.
