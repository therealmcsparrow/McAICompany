## Problem
The CEO waits about 23 minutes for PR checks because the single Windows `npm test` job runs about five times slower than the ubuntu and macOS jobs. A test file that never finishes also holds a job until its 40 minute timeout, with no file name in the output.

## Solution
- Windows CI runs `npm test` as four parallel shard jobs; shard i of 4 passes the matching `--test-shard` value to `node --test`. A failed shard does not stop the others. `npm run check` runs once on Windows, in shard 1. Ubuntu and macOS keep one job each that runs tests and check.
- An aggregate job keeps the name `check (windows-latest)`. It waits for all shards and is red when any shard fails, is cancelled or is skipped, or when the cover check finds a gap. The check names for all three OSes stay as before.
- `npm test` passes every argument that starts with `-` to `node --test` unchanged. Run without arguments it runs the full suite as before.
- Per-file time limit on every OS: without an explicit `--test-timeout`, `npm test` adds a 20 minute limit. A hung test fails by name. A file whose tests are done but whose open handle keeps the process alive is ended by a watchdog after the limit plus up to 30 seconds, with a stderr line that names the file, and the run exits non-zero.
- `npm test` refuses a `--test-timeout` that is not a whole number from 1 to 86400000, and refuses `--test-isolation=none`, with one stderr line and exit 1 before any test runs.
- Test file list: when the environment variable `AICO_TEST_FILES_OUT` names a target, a run writes the test files that completed, one repo-relative path per line, sorted.
- Cover mode: `npm test -- --aico-cover=<dir>` runs no tests. It reads every file list in the folder and reports each file that is missing, ran twice or is unknown, or prints an ok summary and exits 0. CI uses it to prove the four Windows shards together ran every test file exactly once.
- Contract `test-run` moves to v1.1 (minor, additive).

## User stories
- As the CEO, I want Windows PR checks to finish in 8 minutes or less, so I can ship many PRs a day without waiting on one slow OS.
- As the CEO, I want a red Windows shard to block the PR through one check name, so a split job never hides a failure.
- As a builder, I want a hung test file to fail by name, so I find the hang at once instead of after a 40 minute job timeout.
- As a builder, I want `npm test` without arguments to behave as before, so local runs need no new habits.
- As QA, I want proof that every test file ran exactly once across shards, so sharding never skips a test silently.

## Decisions
- Shard count 4 on Windows only; ubuntu and macOS stay unsharded because they already finish in under 5 minutes. Tune the count later from measured data.
- `npm run check` runs in Windows shard 1 only, so it runs exactly once per OS.
- AC7 is met by the aggregate `check (windows-latest)` job. Main has no branch protection or rulesets today, so no required-check rename is needed; turning on required checks is a repo setting for the CEO, outside this run.
- The per-file limit applies to every OS, not only Windows: a hang is a bug everywhere. Default 20 minutes, well under the 40 minute job timeout.
- The watchdog only catches a file kept alive by open handles; a synchronous endless loop that blocks the event loop is not caught, and the CI job timeout stops it.
- Shard and timeout flags travel as plain arguments through the existing test wrapper; no environment-variable fallback.
- Risk tier high: the change touches a Contract (`test-run` v1.1), and a wrong shard split could skip tests silently.

## Testing decisions
- Each acceptance criterion AC1 to AC8 has its own test or CI check, written before the code (QA-first).
- Sharding (AC1, AC2, AC3, AC5) is checked by tests that read the CI workflow, plus the live cover check in CI over the four shard file lists.
- The per-file limit and watchdog (AC4) are tested with hang fixtures that no `npm test` pattern selects, run with a short limit to keep the suite fast.
- Local behaviour without arguments (AC6) and the refusals are tested by spawning the runner.
- AC8, the earlier Windows failure on a main push run, was investigated by QA in this run.
- Success metric: median Windows wall time per PR, first Windows job start to last Windows job end. Target 8 minutes or less over the first 5 PRs after merge; measured by DevOps from GitHub Actions run data and reported then.

## Out of scope
- Sharding ubuntu or macOS.
- Speeding up individual tests.
- Changes to the `golden-warn` and `plugin` jobs or to the checkout path with a space.
- Turning on required checks or branch protection for main.
- Catching a synchronous endless loop inside a test file.
