## Problem
Every Step and the Lead ran under one fixed cap of 95000 tokens with the handover at 85500 (ADR 0047). On models with a large context window that made runs hand over too early, with extra Steps and lost time. A cap stored in settings had no effect. Serves the CEO running aico, who needs a larger default cap that he can change in settings.

## Solution
- The context cap is the setting `pipeline.context_cap`: project over user over the plugin default 180000. Allowed values are whole numbers from 60000 to 1000000. Other values are refused on save with the existing message and nothing is written. A bad value already stored falls back to the level below with a warning line.
- The handover point is always floor(cap x 0.9), so 162000 at the default. The ratio cannot be set.
- The settings get output shows the resolved cap, where it came from and the handover point.
- On the settings page Pipeline tab the Context cap is an editable field at user and project level. The "fixed" badge and the old hint are gone. The hint states the range and the 90% handover, and an "In effect" readout shows the cap and the handover. A refused value shows error text that screen readers announce, and the row passes the page's keyboard and screen-reader checks. The Roles tab shows the same single cap for every Role.
- One cap for every Role and every Risk tier. `roles.<role>.context_cap` is still accepted and has no effect.
- The cap is resolved once at run Setup and recorded in the run state. Every dispatch line (`Context cap: <cap> handover <n>`), the context guard of Steps and of the Lead, the token ledger's over-cap check, the dashboard tokens and the context row of the status line read that run's cap. A setting change mid-run, or a resumed Lead session, keeps the run on its own cap; the next run uses the new value. A flow with no recorded run state uses the current setting, so the dispatch line and the guard still agree.
- A dispatch with no `Context cap:` line means cap 180000, handover 162000. A malformed line gets the same values plus the Nit `invalid Context cap`. If the guard cannot read the run's value it uses 162000, and with no active run it does nothing, as before. The guard reads the cap only from 54000 tokens up, so most tool calls cost nothing extra.
- The plan task budget check takes the run's handover. Its Contract text no longer states 0.8 or 95000.
- Ten Contracts get a minor bump: aico-settings v2.2, run-state v2.1, dispatch-prompt v5.3, context-guard v1.2, lead-handoff v2.3, token-ledger v1.13, dashboard v2.1, aico-mods v2.1, plan-tasks v1.10, handoff v2.7. No key, command or line format is removed.
- ADR 0069 supersedes ADR 0047, and 0047 is marked superseded but kept. README, product spec, user docs, skills and Contracts describe the cap as a setting. The changelog says that a stored `pipeline.context_cap` now takes effect.

## User stories
- As the CEO, I want a default cap of 180000 with the handover at 90%, so Steps on large-window models hand over less often (AC1, AC2, AC9).
- As the CEO, I want to set the cap per user or per project and get a clear refusal for a bad value, so a typo cannot break a run (AC3, AC4).
- As the CEO on the settings page, I want to edit the cap and see what is in effect, using a keyboard or a screen reader (AC5, AC6).
- As the CEO, I want every Step, the Lead, the guard, the ledger and the progress views of one run to use the same cap, even when I change the setting mid-run (AC7, AC8, AC10, AC11).
- As the architect, I want plan task budgets checked against the run's handover (AC12).
- As a reader of the docs, I want no text that still calls the cap fixed at 95000 (AC13).

## Decisions
- One cap for all Roles and tiers, as ADR 0047 intended. The Lead's own guard uses the run cap as well (AC10).
- The cap is frozen per run at Setup, because a change mid-run must not split one run across two caps (AC8).
- The run cap is stored in the existing run state, not a new file, because the guard, the Lead hooks and the ledger already find the run there. One reader serves all three, and one pure formula is shared with the mods.
- The range stays 60000 to 1000000, so existing stored values stay valid and nothing is migrated.
- All Contract bumps are minor. The CEO may call aico-settings a major at the Ship Gate, because a stored value that used to be ignored now takes effect.
- The Core text edits to the handoff and pipeline skills and their references need the Ship Gate approval line. The feature Playbook has no Plan Gate.
- Risk tier high, because the change touches six or more Contracts and the guard hook. No acceptance criterion gets lighter coverage.
- Behaviour change flagged for the Ship Gate and the release note (CRA plain disclosure): settings files that already store `pipeline.context_cap` change run behaviour on upgrade. No other EU law is newly affected.
- This run itself ran on the old 95000 / 85500 cap, because the old code ran it.

## Testing decisions
- QA first: QA tasks wrote red tests for settings resolution, run state and the guard, the ledger and progress views, the plan budget check, the settings page, and the docs sweep before any build task with seams.
- Every acceptance criterion AC1-AC13 has at least one test (AC14). Tests that pinned 95000 or 85500 now assert the new default or the resolved values.
- The docs sweep allows the old numbers only in changelog history and superseded ADRs.
- The settings page row is covered by the existing accessibility checks plus the new refusal and live announcement case.
- The Lead runs the full suite once before the Ship Gate. That run is the pass record.
- Success metric: the share of Steps per run that end with `status: handover`, read from the token ledger. Compare the first 5 runs after release with the last 5 runs at 95000. Target: halved, with zero ledger over-cap exits. Reported in the next feedback run.

## Out of scope
- Caps per Role (later, only if a Role turns out to need a different cap).
- Raising the cap by Risk tier.
- A handover ratio that can be set.
- Detecting the model's context window automatically.
- Migrating stored settings files.
- Rewriting changelog history or the body of ADR 0047.
