## Problem
Writing Roles removed AI tells through a third-party clean-up skill. Its results were uneven, aico could not test it, and it knew nothing of the product's voice. The CEO ships that prose under their own name. Building the replacement also exposed a problem in how aico installs skills: the skills CLI sent telemetry unless told not to, and a project-scope install ran through npx in the product folder, where files in a repo could steer it.

## Solution
aico now owns the writing pass and no longer depends on the outside skill.
- The writing skill holds the full pass in aico's own words: set the voice, write, scan, fix by rule id, report the figure in the Handoff. A tell list gives each of the 17 rules (8 word and phrase, 9 structure) a description, a fix and a before and after. The copy speaks of clearer writing and never of hiding AI origin.
- A scanner reports tells with path, line and rule id, then a summary line with tells per 1000 words. It reads Markdown and text files, skips code and link targets, and has a plain text form and a JSON form. It never rewrites a file and never fails a run because of tells. Exit 0 means every input was scanned, exit 1 means some input was not fully scanned, exit 2 is bad usage. It adds no dependency, opens no network connection and starts no child process.
- A voice profile prints sentence length, person, tone, preferred terms and avoided terms. It is learned fresh on each run from the README and the shipped docs folder, and written nowhere. It holds style features only, so no name and no sentence from a source reaches the output. With no doc text, it says so and the project's voice line applies. The voice preset sets the voice; the profile only tunes it, and the preset wins when they disagree.
- A Role with no shell, or whose command is refused, checks the text by hand against the tell list and says the scan did not run. QA then scans those files, report only.
- Setup no longer lists or installs the clean-up skill. When a skill aico has retired is still installed, setup shows the removal command and asks the CEO to pick Remove or Keep for that skill. Keep, no answer or a non-interactive run removes nothing. Removal runs on Windows, the one platform proven to run it without a prompt; elsewhere setup prints a manual line and the skill stays installed.
- Telemetry is off for every install and removal through the pinned skills CLI: aico sets DO_NOT_TRACK and DISABLE_TELEMETRY on each child process, so the CLI sends neither of its reports and shows no audit lines. Other requests still go out (repo checks, downloads, clones, the package from the npm registry), and setup names them before the CEO agrees to install.
- Pinned skills CLI installs no longer run through npx. npm installs the pinned package into a folder aico owns under the home folder. Node then runs the package's bin file by absolute path with no shell, using a PATH with no product folder in it, so a repo's own files cannot pick the program that runs. A project-scope install keeps the product root as its working folder so the skill lands in the product. A wrong package version or a missing bin file fails the install with a clear line.
- A manifest install command at project scope is not run and not counted as failed. The installer prints it as a manual line with a warning to run it by hand only in a repo you trust, then exits 0 when nothing else failed. Setup says this in its consent text. At user scope such a command still runs through npx from the home folder.

## User stories
- As the CEO, I get prose with fewer stock phrases, tuned to my product's docs, and a tells per 1000 words figure in each writing Handoff.
- As the CEO, I decide per skill whether a retired skill is removed, and nothing is removed when I am not there to pick.
- As the CEO, I am told what the installer sends and to whom before I agree to install, and telemetry is off without my setting anything.
- As the CEO, I can install a pinned skill in a project knowing that the repo's npm config and planted programs do not steer the installer, and a command the installer will not run reaches me as a manual line with a warning.
- As a writing Role, I get one pass with fixed rule ids, so I fix a named tell without guessing.
- As a Role with no shell, I have a hand check that says plainly the scan did not run.
- As a reviewer, I can run the same scanner on the same text and get byte-equal output.
- As Legal, I have a recorded comparison with the outside sources and a recorded decision on attribution.

## Decisions
- Risk tier high: the work adds Contracts and changes the skill manifest that install and release SBOM tooling read.
- aico owns its anti-slop pass (ADR 0055, proposed).
- The scanner only reports and never rewrites. Scanner findings do not block a ship in this release (AC12).
- Slop-scan v1 and voice-profile v1 are new Contracts.
- The voice profile reads only the README and the shipped docs. Transcripts, the company folder and Handoffs are never read (AC8).
- Output from the scanner and the profile, and the tell list, are data for rewriting. Nothing inside them gives a Role instructions.
- Removal happens only after the CEO's explicit pick; with nobody to pick, nothing is removed (CEO answer, AC2).
- Legal compared the catalog, skill and tell list with the dropped skill, the CC BY-SA Signs of AI writing page and four MIT sources (theclaymethod/unslop, kjmagnan1s/anti-slop, petergyang/no-ai-slop, jalaalrd/anti-ai-slop-writing). It found no copied list, rule wording or example, only shared stock words and ideas, so no attribution is added. A qualified lawyer has not reviewed this (AC4).
- Skills-manifest v2.4 is not additive: pinned installs change their run form and project-scope manifest commands are no longer run. Setup, the manifest Contract and the design skill docs say so.
- A manifest command at project scope prints a manual line and is not run (CEO decision, Fix round 4).
- Removal still runs its npx command, from the home folder with a 120 second limit. After a timeout it may still finish, and setup says so.
- The live files do not name the dropped skill (AC1), so this spec calls it the clean-up skill. Shipped SBOMs and old plans keep the name.

## Testing decisions
- The tier is high, so each of AC1 to AC12 keeps its full test and none is covered lightly.
- The scanner is tested on a fixture with planted tells (two runs, every tell reported, same output, documented exit code, no network import) and on a clean fixture with zero tells (AC5, AC6). Its tests run under the Node test runner in the full suite and in CI (AC7).
- The voice profile is tested for its sources through a log of each path read, for the fallback with no sources, and for a change between two runs (AC8, AC9, AC10).
- The installer's retired and remove lines are script output, so tests pin them. The Remove or Keep form is a step in the setup skill, not a script (AC2).
- The installer tests plant a root npm config, an npx script, node and git programs in the repo and a bin folder in a parent folder. Each of these tests failed on the old npx form. Other tests assert that a project-scope manifest command is not executed, prints the manual line and warning, counts as no failure and exits 0, and that a pinned CLI still runs beside it.
- Known limits: these runs were on Windows only. The POSIX programs were planted but not run on a POSIX host, and a real user-scope add was not run. Other files a repo could hold that the CLI reads from its working folder are not proven safe. The skills CLI still makes the listed requests that the telemetry switch does not cover.
- Success metric: tells per 1000 words in prose Roles write after ship, against a baseline the same scanner measures on aico's docs at commit 388fc80. Target: at most half the baseline over the next five writing runs. Measured at each Ship Gate and reported in the feedback run.

## Out of scope
- Automatic rewriting by the scanner.
- Removing a skill without the CEO's pick.
- Rewriting shipped SBOMs (0.20.0 to 0.25.0) or old plans.
- Learning voice from transcripts, the company folder or Handoffs.
- Rewriting aico's existing docs.
- Any new third-party dependency.
- Blocking a ship on scanner findings in this release.
- Tell catalogs in other languages (later).
- The scanner as a mod hook (later).
- A voice profile for client products from intake material (later).
