## Problem
The CEO cannot give a Role its own third-party skills. The three old skill lists worked per stack or per project, never per Role, and project text could feed what got installed. The user served is the CEO running an aico company: expert solo founders, consultancy owners and agency leads, including a keyboard-only screen reader user.

## Solution
One skill catalog, a choice per Role in settings, and one dispatch line that tells each Role what to load. aico never runs a stored command, and running nothing is also how it reports status.

- Catalog: the third-party skills file replaces the old skill manifest. It has two layers with one schema. The baseline ships read-only with the plugin; the user layer sits in the user's home, outside the plugin cache, and survives a plugin update. A product folder never supplies an entry, a command or a path, and an env value cannot move the read path.
- Entry: a name, one source (repo, installer command or plugin), one category from a closed list of seven, a license as the CEO stated it, and optionally a commit, a vetted date and a bound hash. A repo in the user layer needs a commit.
- Selection: on the Skills tab of settings the CEO picks up to 5 skills per Role, at user or project level, from entries whose category fits the Role. A sixth pick is refused with "Limit reached: a Role can have 5 skills. Clear one first." Protected Roles select at user level only. A project stores names only.
- Dispatch: every Role gets a `Role skills:` line holding only its own names, or `none`. It replaces `Design skills:`. A name reaches the line only when its status allows it; otherwise it is left off and the run records `degraded: missing <name>`.
- Add: `aico:add-skill` asks name, repo, installer command, category, commit and license in a form, previews, and writes on Save only. It installs nothing. With the same repo and another commit it offers to move the pin; with a baseline repo and a commit it pins that baseline entry.
- Install: a run start asks Install or Skip per selected repo skill with a commit that is not there yet. The installer scans the pinned commit, installs it, compares the installed folder to the scan, scans the installed folder and only then stores the hash and vetted date. A failed scan leaves the skill off every Role's line. A stored command only ever prints as a `manual` line with a warning.
- Status: each skill shows one status as text, with the place found, a license text and a vetted text, on the settings page, in the installer's status option and in the run-start form. Computing it starts no process, reads no command text and makes no network call.
- Migration: lines in the two old project profile skill sections are no longer read. One form offers Migrate or Later and shows the result per line. Unmigrated lines fail closed: not dispatched, not installed, counted as degraded and named in the Gate summary until migrated.
- Research: an approved set from a design or skill researcher is recorded as user catalog entries and selections on the Roles the CEO chose, with the license the CEO stated. Research can never introduce a new command. Design research reruns when the design selections are stale, by a 180-day approval date.

## User stories
- As the CEO, I select several skills for one Role in settings and they stay selected after reload.
- As the CEO, I see per Role only the skills that fit its category, each with its source, status, license and vetted text.
- As the CEO, I add a skill by answering a short form, and a stop before Save writes nothing.
- As the CEO, I see in the run-start form what will be installed, with the exact command and destination, and can skip it.
- As the CEO, I can tell whether a skill is really there, or only a folder of that name, without aico running anything.
- As the CEO, I move my old project skill lines into the new model through one form, and nothing changes until I say so.
- As the CEO, I clone a repo and know it brought me no catalog entry, no command and no skill a Role will load unproven.
- As a Role, I get one line naming the skills chosen for me, load each one and report any that is missing.
- As Ravi, on keyboard with NVDA at 400% zoom, I can select skills and hear state and status as text, with focus kept after save.

## Decisions
- The catalog replaces the old manifest, in one schema with two layers: repo-owned trust stays with the baseline, and a cloned repo cannot supply entries or commands (CEO: "Replace").
- Both old project sections merge into the per-Role model in this run. Old `## Skills` lines had no Role, so the CEO chooses Roles and category in the migration form (CEO: "Merge in this run").
- A stored command is kept and shown, never run by aico, with an exact version and no shell operators (CEO: "1, but give status if installed").
- The CEO selects; Roles never pick at run time and the Skill tool is not blocked at run time. Prototype skipped by the CEO.
- Cap of 5 per Role, because each loaded skill eats the context cap. Protected Roles select at user level only, because a third-party skill can steer a reviewer's verdict.
- Every user entry needs a license as the CEO states it, and nothing checks it. A baseline entry may have none, shows `no license on record` and still works, so setup commands stay byte-equal; no license is inferred. Baseline licenses are sourced values, and the three names with none sit under a CEO exception to security rule agentsec.M-SEC6.
- A vetted date records one clean scan of one commit and is no safety claim. Every Install scans again. Old `approved` dates never become vetted dates; old vetted dates move as they are and read "from the old list, not scanned here" until a scan binds a hash.
- No re-approve control for design research: a stale set leads to the research Step, whose approved set renews the date. An unchanged save renews nothing, and a missing date counts as stale.
- Mixed selection: a skill any Role selects at user level is read only from the user home, so a repo's folder alone reads `missing` or `not found`. At project scope a name in both places reads as project.
- Name-only passes dispatch only at place user with a clean catalog read, narrower than the status word in AC6. A folder of that name in a product root can come from a clone, and with any catalog error or warning a lost pin may be why it looks fine. A project-place name gets a form that names the place, and no answer puts it on a line.
- A selected baseline repo skill with no pin gets a `needs a pin` line and no scan or install, which narrows AC11's baseline clause; setup groups still install baseline entries as before. The user pins it through `aico:add-skill`.
- The stored hash is cleared before each new scan, so a failed scan leaves another product's copy at `folder not recognized` until reinstalled, the same cost as moving a pin.
- If clearing a pin would change which row of the name is read, it writes nothing, runs no scan and installs nothing, and names the row by number. The stored hash stays, and the skill stays off every Role's line until fixed by hand. In that refused case a vetted date on the row can stay, the one narrowing of AC12, and it reads "from the old list, not scanned here". Writing stored rows back unchecked during a clear is the one CEO-approved exception to refusing banned values.
- The settings page labels a command entry `command (manual)` and does not print the command text; the exact command appears in the run-start form and the `manual` line.
- Breaking Contract changes approved through the Ship Gate: `skills-manifest`, `dispatch-prompt`, `skill-recommendation`, `research-report`, `design-skills-section` and `skills-section`, plus the new `skill-catalog` Contract. A clone no longer brings its skills: a teammate sees selections reported as not in the catalog until they add them.
- Laws: third-party components stay traceable in the SBOM and every new install path stays pinned and scanned (CRA). The catalog holds no personal data, so GDPR is not triggered.
- Success metric: Role skill load rate, target at least 95%: names on `Role skills:` lines minus `missing role skill:` lines, over names on those lines, across the first 5 feature runs after merge, measured by the aico feedback command from the run folders.

## Testing decisions
Risk tier high: no criterion is covered lightly and each has its own test. A planted side effect, a planted binary on PATH and planted repo files prove the never-run and never-read rules. A hands-on or accessibility tester tries AC8 with AC15's setup, since free text through "Other" under NVDA is unproven. Security checks at audit that a personal copy wins over a repo's folder of the same name, since AC17's home-copy case rests on it. Acceptance criteria:

- AC1: Given a valid catalog with several categories, When the settings page opens, Then each Role lists only entries whose category maps to it, each with name, repo or command, and status (AC17). A wildcard baseline entry is shown as not selectable, with the reason.
- AC2: Given an entry that fails validation (missing field; malformed license on any entry; missing license on a user entry, a user pin of a baseline entry included; unknown category; bad pattern), or a user file that is oversize, a link or bad JSON, When read, Then the page names the entry number and field without echoing its text, the entry cannot be selected, and nothing from it installs or prints as a `manual` line; baseline entries still work. Given a baseline entry with no license, plugin entries included, When read, Then it is valid and can be selected, no license is inferred or filled in, AC17 shows it as having none, and AC19's commands stay byte-equal (test).
- AC3: Given a Role with at least two matching entries, When the CEO selects them and saves at user or project level, Then all stay selected after reload; a 6th selection for one Role is refused with a reason.
- AC4: Given a save or a stored value naming a skill outside the Role's categories or not in the catalog, When saved, Then it is refused; When already stored, Then it is ignored at resolve time, reported in `ignored`, never dispatched.
- AC5: Given a project-level selection for a protected Role (`architect`, `code-reviewer`, `fresh-reviewer`, `pentester`, `security`, `vuln-scanner`), When resolved, Then it is ignored and reported; only the user level selects for those Roles.
- AC6: Given Role A with selections and Role B with none, When each is dispatched, Then A's prompt has `Role skills: <names>` with only A's names and B's says `none`; no prompt holds another Role's selections or a `Design skills:` line, and every Role gets the line except where the `dispatch-prompt` Contract omits it (Reprompt Step). Given a selected skill that, after the run-start forms, has an AC17 status other than `installed` or `installed (name only)`, or is a plugin entry not in the session's skill list, When its Role is dispatched, Then the name is left off that Role's line, the run records `degraded: missing <name>` once per name, and a Role with no name left says `none` (test, including a folder planted by a repo under a user-level selection of a protected Role).
- AC7: Given `Role skills:` naming an available and an unavailable skill, When the Step starts, Then it loads the first and writes `missing role skill: <name>` under `## Next`; a name its agent text also loads (`aico:ui-design`) loads once.
- AC8: Given `aico:add-skill`, When the CEO runs it, Then a form asks in turn name, repo, installer command, category, commit and license; category offers only the closed list. A preview offers Save / Cancel and says: the license is what the CEO stated and nothing checked it; a repo entry stays `not vetted` until an install scans it clean; a command-only entry is never scanned and stays `not vetted`. Any stop before Save writes nothing.
- AC9: Given an invalid answer (name or repo outside the patterns, neither repo nor command, repo without 40-hex commit, command without exact `@x.y.z` or with a shell operator or invisible character, license empty, over 64 characters or with an invisible character) or a taken name (in the user file with the same source and commit, or with another source; in the baseline, except the pin case below), When entered, Then the field and reason are named, it asks again and nothing is written. An invisible character is any of general categories `Cc`, `Cf`, `Zl`, `Zp`, every `Default_Ignorable_Code_Point`, U+180E, U+2065 and tag characters U+E0000-U+E007F; space separators (`Zs`) are not, so `MIT License` passes. A value holding one is refused at add, at `role-skills record` and on read of the user file, by field and never echoed (test: U+202E, U+200B, U+3164). Any other license text is accepted as stated, with no check against a list or the repo. Given a name in the user file with the same repo and another commit, When the commit is entered, Then a pin form offers Keep (Recommended) / Move / Cancel: Keep and Cancel write nothing; Move says other products read `folder not recognized` until reinstalled, then goes on to the license question and the preview; Save changes only that entry's commit and license and clears its `hash` and vetted date, its category and every selection stay, and a stop before Save writes nothing. Given a name in the baseline, not in the user file, with the same repo and a commit, When saved, Then it is a user pin with the license the CEO stated, not a taken name.
- AC10: Given Save, When the user file is absent it is created; When present the entry is added atomically and all others keep their values. Baseline entries ship with the plugin and are read-only; user entries live outside the plugin cache and survive a plugin update. Given a repo with a planted catalog file, project setting or Claude Code project settings env value, When any script reads the catalog, Then no entry or command comes from it and the read path does not move (test). On a name clash the baseline wins and the clash is reported, except a user entry with the same source and a commit, which pins it.
- AC11: Given a selected repo entry not installed, When a run starts, Then the Install / Skip form shows the exact command and the destination lines. User entries install at the scope of the selection (project selection: no `-g`, in the product root; user selection: `-g`), with the commit pin; baseline entries at user scope as today. Selecting and `aico:add-skill` install nothing. Skip records `degraded: missing <name>`.
- AC12: Given Install on a user repo entry, When it runs, Then it first passes the same scan and approvable rule as the skill picks vet command on that commit, installs through the v2.4 run form, stores the bound hash and records the date of the clean scan as the entry's vetted date. Every Install scans again; a stored date skips nothing. A failed scan installs nothing, removes any earlier vetted date and reports the skill missing. Given a user entry with no license, When a run starts, Then AC2 applies: no scan, no install, and the page names the `license` field (test).
- AC13: Given any entry with a command, baseline or user, When the installer script handles it, with or without `--dry-run`, Then it prints `manual <cmd>` and the `WARNING:` line and never executes it. A test plants a command with a visible side effect and proves it did not happen.
- AC14: Given a product with lines in `## Design skills` or `## Skills`, When a run or `aico:setup` starts, Then one form lists them with Migrate (Recommended) / Later. Migrate shows per line the result (entry, category, Roles), adds entries to the user catalog and selections at project level, carries each `approved` date, archives the lines under the company folder and removes them from the sections; a re-run changes nothing. Nothing is installed or uninstalled. With nobody to answer, nothing changes.
- AC15: Given Ravi (NVDA, keyboard only, 400% zoom), When he selects skills on the page, Then every control has a visible label, state and status are announced as text, focus stays put after save and nothing scrolls sideways (WCAG 2.2 AA, `aico:ui-design`).
- AC16: Given `aico:add-skill help`, When run, Then it prints usage from the add-skill command doc and changes nothing; the skill has `disable-model-invocation: true`; README, the settings command doc, the glossary and the changelog (as a breaking change, with the migration) describe the feature; setup, stack-detect and README point to `aico:add-skill`, not the old skill manifest.
- AC17: Given catalog entries, When the CEO opens the settings page (per Role, on each skill's row) or runs the installer's status option (one line per skill, naming its Roles), or a run start shows its form, Then each skill has one status as text plus the place found (user or project): repo entry with commit: `installed` = folder under the Claude or agents skills folder whose hash equals the bound hash; `folder not recognized` = folder present, hash differs or none bound; `missing` = no folder. Command-only or unpinned baseline entry: `installed (name only)` = folder or link of that name, version not checked; `not found` = none, which is not proof, since an installer may write elsewhere. Plugin entry: `checked at run start` on the page, in the session's skill list or not at run start. For any entry but a plugin that any Role selects at user level, even if another Role selects it at project level: only the user home is read, so a folder or link of that name under the product root alone reads `missing` (repo entry with commit) or `not found` (command-only or unpinned baseline), whatever its hash, and a copy in the user home beside it gets that copy's status, place user (test). Each skill also shows, as plain text and never as markup, its license labelled as stated and not checked, or `no license on record` for a baseline entry with none, and `vetted <YYYY-MM-DD>` when a user entry has a date and a bound hash or a baseline entry has a date, `vetted <YYYY-MM-DD>, from the old list, not scanned here` when a user entry has a date with no bound hash, else `not vetted`. A command-only entry always shows `not vetted`, even if the file holds a date (test). `no license on record` never blocks selecting, installing or printing a baseline entry (test).
- AC18: Given an entry whose stored command has a visible side effect and a planted binary on PATH, When any status is computed, Then no child process starts, no command text is parsed or run, no network call is made and no file content is read through a link (where a link leads and which names are there may be looked up) (test).
- AC19: Given the merged run, When `aico:setup` runs with `core`, `research`, `go`, `react`, `tanstack` or `auth`, Then the commands equal today's byte for byte, `include` still expands; the structural check keeps its name, source and license checks on the baseline; the SBOM lists the same components from the baseline and never a user entry; `--retired` does not flag a name in the user catalog. The old skill manifest is gone and a check fails if it returns or a live skill, script or Contract cites it as a source.
- AC20: Given migration, When a line is handled, Then the preview shows its validated values per the Contract, no license or vetted question is asked, no value is guessed, and: name and source equal a baseline entry, no commit → selection only; name and source equal a baseline entry, with a commit → a user pin (AC10) holding that commit and the line's own license and vetted date, never the baseline's; other repo line with commit → a user entry holding the line's license and vetted date, with no `hash`; repo line without commit → stays, reason named, nothing guessed; command line → selection only when byte-identical to the baseline `install` of the same name or the known old `impeccable` form, else stays; plugin line `aico:ui-design` → selection of a baseline plugin entry, never installed, its `license: -` and `vetted: -` allowed; any other plugin line → a user entry when the line holds a license, else stays, reason named, never installed; a repo or command line with no license or `-`, or any value failing its pattern → stays, reason named, text never echoed; name in the baseline with another source → stays, reason named; name in the user file: same source and commit → selection only, same source and another commit → the AC9 pin form (Keep: the line stays, reason named; Move: commit and license from the line, `hash` and vetted date cleared), other source → stays, reason named; a Role over 5 → the extra stays. `## Design skills` lines offer the five UI Roles first; `## Skills` lines offer a CEO choice of category and Roles, since they had none.
- AC21: Given unmigrated lines after Later, When a run proceeds, Then they are not dispatched or installed and do not stop other installs, the run records `degraded: unmigrated skill lines <n>`, the Gate summary names the count and the form returns next run. The old group names `design` and `skills` are not an install source any more.
- AC22: Given a CEO-approved `design-researcher` or `skill-researcher` set, When the Lead records it, Then it writes user catalog entries plus the Roles and the license of each new entry that the CEO gave in the form (Roles only recommend), never a project profile skill section and never a vetted date; a new entry with no stated license is not written and is named in the form's result; a researcher's command source is accepted only if byte-identical to a catalog `install` of the same name, so research cannot introduce a command; researchers judge the resolved selections and catalog; Install / Skip stays a separate form.
- AC23: Given a product with UI, When `aico:feature` decides the design research Step, Then the set is stale when no UI Role has a resolved `design` selection, or the newest approval date on those selections is over 180 days old or there is no valid date on any of them. The date sits with the selection (baseline is read-only). A settings save sets today's date on the selections of each Role whose selection it changes; other Roles keep their dates. Recording a CEO-approved research set (AC22) sets today's date on the selections it records, even when they are unchanged. Migration keeps the old date. There is no separate re-approve control.
- AC24: Given a new or empty product, When profile setup runs or the page opens, Then the project profile holds neither old section (the project template), no migration form shows, and with no user catalog the page lists baseline entries, a line naming `aico:add-skill` and no error.

## Out of scope
- Steno work; a new plugin dependency.
- aico running a stored command, or running anything to check status.
- A catalog in a product folder; a repo supplying entries, commands or read paths.
- A migration without a CEO form; deleting old lines without an archive; removing installed skill folders.
- Roles picking skills at run time; blocking the Skill tool at run time; ranking or searching for skills.
- Later: removing or editing entries through a command; plugin entries through `aico:add-skill`; pinning the baseline's repo entries; a catalog a team can share, which needs its own security design; skill audit round 2.
