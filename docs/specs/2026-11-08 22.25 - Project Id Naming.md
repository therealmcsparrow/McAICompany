## Problem
One piece of work goes by several names: a dated Topic folder, a branch slug, a bare ticket number like `T3`. The CEO, running aico Lead sessions on own products, has to translate between them, and agents can mix up tickets of different runs. One ID that every agent, file, ticket and branch uses removes that ambiguity.

## Solution
Every Playbook run that makes a work folder belongs to a project with one project ID.

- Project ID: `P<yyyymmdd>.<n>`, for example `P20261108.000001`. The date is a real calendar date in local time. `n` counts per day per repo, starting at `000001`, zero-padded to six digits; past `999999` it grows to seven digits and more, never with a leading zero, at most nine. All zeros, a lowercase `p`, fewer than six digits, an extra dot or path characters are refused.
- The next ID is one more than the highest number of that day found among the work folders and the archive on disk. No counter file, no new storage.
- Run folder: `<ProjectID>-HH.MM.SS`, one per run of a project (first run, later draft, build or fix run). Every run of a project reuses its ID; a later run gets its own folder with its own start time. A clash in the same second is refused for a later run and nothing is created; a new project then takes the next number.
- Each run folder holds a summary file made at creation: line 1 the one-line description (1 to 120 characters, no control or invisible characters), line 3 `Run: <kind> <playbook>`, and for split projects line 4 `Siblings: <the other IDs>`. A missing or multi-line description fails lint.
- Ticket ID: `<ProjectID>-T<n>` everywhere, plan headings, ticket records, dispatch `Task:` lines and commits included. A bare `T<n>`, or a ticket ID of another project, is refused in a new-style run. File names inside one run folder keep the short `T<n>`.
- Branch: `aico/<ProjectID>`, one per project, used by every run of it.
- Split: when an idea or bug holds several unrelated tasks, the Product Manager proposes the split in the brief and the CEO confirms it. Each task gets its own project ID, folder and summary; the first task keeps the original ID and every summary lists its siblings.
- The ID rules live in one shared module; every consumer (scripts, mods, lint, ledger, dashboard, Playbooks) reads names through it.
- Old names stay readable: legacy slugs and dated Topic folders still resolve and resume. Nothing is renamed.
- Every CLI that receives a bad ID or folder name prints `refused: <reason>`, exits 3 and writes nothing.

## User stories
- As the CEO, I name one project ID and every agent, folder, ticket and branch of that work answers to it.
- As the CEO, I see a one-line description of each run without opening its Handoffs.
- As the Lead, I dispatch `P20261108.000001-T4` and no agent can confuse it with ticket 4 of another project.
- As the CEO, I resume an old Topic-named run exactly as before.
- As the Product Manager, I split an idea into separate projects and each one links to its siblings.

## Decisions
- Format `P<yyyymmdd>.<n>` with at least six digits: fixed width sorts as text up to 999999 (CEO).
- Counter per day per repo, derived from folders on disk: no shared state to drift or lock.
- The time marker inside a project includes seconds (`HH.MM.SS`), so two runs in the same minute do not clash.
- Full `<ProjectID>-T<n>` ticket IDs everywhere, no short alias (CEO).
- One branch per project; worktree refs are shared by runs of one project, one run of a project at a time.
- Legacy folders and branches are never renamed (CEO).
- Contract: work-folder-name moves from v1.1 to a new major (CEO approved), with minor versions in its consumers; the installed version cited here is work-folder-name v1.1.
- Success metric: share of references to a run in Handoffs, ledger lines and commit subjects that use the project ID; target 100% over the first 10 runs after release; measured by search at the next aico feedback run.
- Laws: none apply. Internal file naming, no personal data, no AI output, no consumer sale.

## Testing decisions
Risk tier high: every criterion AC1 to AC10 has its own test, none covered lightly. Tests drive the shared module and each consumer command, including refusals, legacy names, same-second clashes, the rollover past 999999 and the one-home guard for the ID pattern.

- AC1: Given no project today, When a run starts a new project, Then a run folder `P<today>.000001-HH.MM.SS` exists and the CLI prints the ID, folder name and branch.
- AC2: Given a project exists that day, When a second new project starts, Then it gets the next number; a new day starts at `000001`; after `999999` comes `1000000`.
- AC3: Given a project, When a later run continues it, Then a new run folder with the same ID is made; a same-second clash is refused and nothing is created.
- AC4: Given a new run folder, Then its summary holds a one-line description of at most 120 characters; a missing or multi-line one fails lint.
- AC5: Given a plan in a project, Then every ticket ID is `<ProjectID>-T<n>`; ticket approval, plan check and commits accept it and refuse a bare `T<n>` or another project's ID.
- AC6: Given a project, Then its branch is `aico/<ProjectID>` for every run.
- AC7: Given legacy slugs and dated Topic folders, When dashboard, idea flow, plan check, run state or ledger read them, Then they resolve and resume as before; none is renamed.
- AC8: Given an idea with N unrelated tasks and a CEO-confirmed split, Then N project IDs, folders and summaries exist, the first keeps the original ID and each summary lists its siblings.
- AC9: Given a bad ID or folder name, When any CLI receives it, Then `refused: <reason>`, exit 3, nothing written.
- AC10: Given the new shape in a Handoff `task:` or dispatch `Task:`, Then handoff lint passes; the ID pattern lives in one module only.

## Out of scope
- Renaming existing folders or branches.
- Descriptions or suffix words such as Build or Draft in folder names.
- Counters across days or a shared counter file; any new storage service.
- A short `T<n>` alias outside one run folder.
- Later: dashboard search by project ID; the ID in pull request titles.
