## Problem
Long aico runs printed nothing until they ended: the full test suite takes about ten minutes, and a rule-check node-test run can wait up to 480 seconds on a buffered child. Role background runs were just as quiet. The CEO could not tell progress from a stall. This run retrofits the progress rule proj.M15 onto the existing long commands and keeps the quick ones as they are.

## Solution
- Three long commands report progress on stderr: `npm test` (full and scoped runs), the full repo check (`npm run check`) and `rule-check run`. Stdout, exit codes and refusal lines stay byte-identical to the base commit.
- One shared line format, plain text, one line per event, LF only, no ANSI colour, no carriage-return redraw, the same in a terminal and when piped to a file. The prefix is literally `aico test`, `aico check` or `aico rule-check`:
  - start: `aico <cmd>: start, <total> <unit>`, where the unit is files, phases or checks.
  - item: `aico <cmd>: <n>/<total> <item> ok` or `fail`.
  - heartbeat after 10 seconds with no line: `aico <cmd>: still running <item>, <s>s` while an item runs (time since that item began), `aico <cmd>: still running, <s>s` between items (time since start).
  - end: `aico <cmd>: end, <ok> ok, <fail> fail, <s>s`, with the time since start.
  - Seconds print with one decimal and no space, such as `0.1s`.
- An item is only a test file path, a check phase name or a rule-check id. Control, format, line-separator and default-ignorable characters (proj.M-SEC9) become `?`, and the item is cut to 120 characters. No rule text, file contents, secrets or names.
- `npm test` runs node's test runner through a wrapper with the same globs. Node's own reporter output stays on stdout, the progress reporter writes to stderr, the exit code passes through, and a signal ends with 1.
- The full check counts a phase as failed when it added an error; warnings do not fail it. `rule-check run` prints progress once its bindings load, and an out-of-date binding counts as a fail. A check with no rows passes.
- Quick commands are exempt and keep today's stderr byte for byte: the drift and packs modes of the check, handoff lint, plan check, spec check, review loop, run state and the other run subcommands. The same goes for the rule-check modes other than `run` and its early returns.
- Library calls stay silent: only the command-line entry turns progress on, so in-process callers see no change.
- The tdd, review and verify skills and the QA Role now tell a Role to use a streaming reporter on a long run and never to silence or fully buffer it. The Role also names in its Handoff where the output went.
- The changelog and the README maintain section describe the format.
- Spec-path fix: the spec check and the draft input now accept the committed spec of a nested run, named by its flat run key in the specs folder (destination-spec v1.5, draft-input v1.8), so a nested run's shipped spec is committed with the ship; every older spec path behaves as before.

## User stories
- As the CEO, a ten-minute test run shows which file it is on and a heartbeat at least every 10 seconds, so I can tell work from a stall.
- As the CEO, a rule-check waiting on its node-test child still shows a heartbeat.
- As the CEO, the last stderr line of a long run tells me how many items passed and failed and how long it took.
- As a Role running tests in the background, my piped log still holds plain progress lines, and I name its location in my Handoff.
- As a script reading stdout or exit codes, I see no change.

## Decisions
- The line format is the one the shared helper ships. The plan was amended to match it in Fix round 1: every criterion holds with it, and its tests already pin it.
- One shared helper serves all three commands, because per-command copies drift and the CEO prefers slim designs.
- The heartbeat runs on a worker thread, so the synchronous check and rule-check stay synchronous and still print while a child process blocks the main thread. No heartbeat can follow the end line.
- Every progress write ignores its own errors. A lost line never changes stdout, the exit code or a refusal.
- Quick commands get no start or end line: their exit code already gives the outcome, and many tests pin their exact stderr.
- Progress lines never start with `not ok` or a cross mark, because rule-check reads failing test names from the test output.
- The progress format gets no Contract. The full check is Core and now imports the progress Module, which has no Contract. The CEO decides this at the Ship Gate. Recommended: accept now, and promote the format to a `progress-line v1` Contract when a stall alert starts to parse it.
- The only Contract changes are the additive minors of the spec-path fix (destination-spec v1.5, draft-input v1.8). The spec uses the flat run key rather than a subfolder, because the key already exists and the specs folder keeps no subfolders.
- Risk tier high because of the Core edit and the Contract change. Every criterion has its own test.
- Success metric: the longest silent stderr gap during one full `npm test` and one rule-check node-test run, target 10 seconds or less (before this run: the whole run, about 600 seconds). A QA Step times it at the Ship Gate and again at the first aico feedback run after the ship.
- Laws: GDPR is covered, since progress lines carry no personal data. CRA, the AI Act, the EAA and VAT rules do not apply: this is dev tooling with no new input surface, no network and no eval.

## Testing decisions
Risk tier high: every criterion has its own test. Tests drive each command as a child process on fixtures that pass, fail and run slowly, in non-TTY mode, and assert on stderr lines, stdout bytes and exit codes. The heartbeat interval has a test seam, so the tests stay fast.
- AC1: Given a long command, When it starts, Then the first stderr line names the command and its item count.
- AC2: Given a long command, When an item finishes or 10 seconds pass with no line, Then an `n/total` item line or a heartbeat appears, including while rule-check waits on node-test.
- AC3: Given a long command, When it ends, Then the last stderr line gives the ok and fail counts and the seconds.
- AC4: Given each long and quick command on the base input, When stdout and the exit code are compared, Then they are byte-identical.
- AC5: Given a quick command, When it runs, Then its stderr matches the base, refusals included (one table-driven test).
- AC6: Given `npm test` piped to a file, When it runs, Then the start, per-file, heartbeat and end lines appear as plain lines.
- AC7: Given any progress line, When it prints, Then it holds only command, item ids or paths, counts and times, with unsafe characters as `?` (one table-driven test).
- AC8: Given the tdd, review and verify skills and the QA Role, When a text check reads them, Then each tells a Role to stream long runs and name the output location.
- AC9: Given the full suite and the full check, When they run at the Ship Gate, Then both pass with the new progress tests included.

## Out of scope
- Spinners, carriage-return redraws, colour, and a quiet or verbose flag.
- Progress on quick commands. Any stdout, exit code or refusal change.
- A Contract for the progress format, and any Contract change beyond the spec-path fix.
- Later: a stall alert that warns the Lead after N seconds of silence, and a dashboard showing the last progress line.
- Known limits, routed as Nits: a full-check phase that throws prints no end line; the test wrapper counts files from the repo root, not the working folder; a heartbeat can, rarely, print just after an item line; the heartbeat interval setting is not in the user docs.
