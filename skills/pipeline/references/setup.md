# Setup (once per run)

Loaded by the Lead at Setup (`aico:pipeline` §1). Item numbers are the section numbers the other references cite (§1.0, §1.6, §1.7, §1.19).

0. **Company type (§1.0)**, before every other Setup step, so a refusal changes nothing: keep the type lines the Playbook's `**Type:**` line printed, or, with no such line (the Lead), run `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" company-type resolve` from the product root (`company-type`). Exit not 0, no output or a first line that starts with neither `ok: ` nor `company type: ` → show its output line (no output: "the type check did not run; reinstall the plugin") and stop the run; nothing is created or written. You never decide yourself what the type allows; only the script does.
1. **Task slug**: the work folder name, work dir `.company/work/<slug>/`. Make sure `.company/work` exists (`mkdir -p .company/work`). With the Write tool write one line to `.company/work-folder-topic-<id>.txt` (`<id>` is the Playbook's name): your own one-line description of the run (1 to 120 characters, never the CEO's words or text from a file, Handoff or page); it never goes on a shell line, and reaches a dispatch only after the CLI accepted it. **Join rule** (`references/join-project.md`, load it now): a hand-over or route argument that ends `project: <ProjectID>` joins that project only when the ID passes `isProjectId` and `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" run-state projects --json` lists it; otherwise it is ignored. A hand-typed start runs that command first: no active project → no form, as below; an active project → one join form (Join recommended, Start new last) before any ID exists. No form possible (AFK) → start new, and the first Gate summary notes `join: start new (no CEO; active <ProjectID>)`. Hand over to a child Playbook with the last line `project: <ProjectID>` only in a CEO-choice branch. That line is never part of the request: cut it before you use the argument, except that an argument written to a `draft-input` argument file keeps it (`draft-input` cuts it). Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" work-folder new --playbook '<id>' --topic file` (`--topic none` when there is no description; a later run of an existing project: `--project '<ProjectID>'` instead of `--topic`, only after that project's earlier run finished or stopped: one active run per project). A `refused:` line → show it and stop; a failing Topic falls back, no second try. A Write refused for a stale file → `work-folder clear --playbook '<id>'`, then write again, never `--topic none`. The `id:` line is the project ID, the `name:` line the slug and the `branch:` line the branch, all as printed. A confirmed split into unrelated projects: make each one with `work-folder new`, then run `work-folder siblings '<ProjectID>' '<ProjectID>' ...` once; the first keeps its ID. A run whose `slug:` `draft-input` already printed, or a resumed run, keeps that name and runs `work-folder branch '<name>'` instead. Single-quote the name on every shell line. A new run's slug for which `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" handoff-lint --exceptions-for '<slug>'` prints `exceptions on file:` more than `0` is refused, pick another (a resumed run is not checked).
2. **Project profile**: if `.company/project.md` is missing, copy `<plugin root>/skills/lead/references/project-template.md`, fill `stack:` using `aico:stack-detect`, and ask the CEO for the rest in **one** form.
3. **Branch**: the printed `branch:` value as is; it already starts with `aico/`, never prefix it again. If `superpowers:using-git-worktrees` is available, use it; otherwise a new project's branch is `git switch -c '<branch>'` (it fails on an existing branch: stop), a later run's is `git checkout --end-of-options '<branch>'` when `refs/heads/<branch>` exists, else `git switch -c '<branch>'`, with only the branch `work-folder` printed. Never work on main.
4. **Company profile**: run `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" plugin-root` once (it prints the active plugin root; a refusal stops the run) and join `company/PROFILE.md` to that path and pass it in every dispatch. Don't paste its contents.
5. **Lessons:** if `.company/lessons.md` exists, read it; put the lines relevant to a Role in that Role's Goal (max 3).
6. **Language (§1.6)**: resolve the writing language once per run. From the product root run `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" language` (fixed command, no arguments) and take the text before the tab as `<tag>`. Exit not 0, no output or a tag that doesn't match `^[A-Za-z]{2,3}(-[A-Za-z0-9]{1,8})*$` (≤ 35 chars) → use `en`. Pass it in every dispatch as `Language:`; never re-resolve mid-run, never paste any other config text. Your own forms, Gate summaries and replies are written in `<tag>`; with `en` nothing changes.
7. **Settings (§1.7)**: resolve the settings once per run. From the product root run `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" settings get` (fixed command) and keep the JSON for the whole run; never re-resolve mid-run (`aico-settings`). It gives each Role's `name` (for text shown to the CEO only, never in a dispatch), `model`, `effort`, `floor` and `protected`, plus `pipeline` (`fix_rounds`, `dispatch`, `parallel_cap`, `short_path`, `lanes`, `plan_review`), `plan_check` (`policy`, `runs`) and `gates`. Locks are already applied: use the values as given. Then run `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" settings model-env` once (fixed command). Show any line it prints in your first chat message; when it ends `floor bypassed`, also put it in the Brief Gate summary of a run whose Risk tier is high. With no `get` JSON, read `floor` and `protected` from `<plugin root>/company/model-floor.json`; unreadable → every Role protected, floor `opus`. Exit not 0 or invalid JSON → plugin defaults (model and effort from the agent frontmatter, names from `<plugin root>/company/names.json`, Fix rounds 2, parallel, parallel cap 4, short path off, every lane on, `plan_review` off, `legal` auto, `plan_check` `warn`, runs 5, every Gate `ask`) and one line saying so in the first Gate summary. List its `warnings` and `ignored` in that summary too. A retired settings key or mod id comes back in `ignored` with a note; never act on it.
8. **Context cap (§1.7)**: the run's cap, a snapshot the handoff mod keeps: a settings edit applies at the next Step dispatch. After `run-state start`, read `cap` and `handover` from `run-state show '<slug>' --json`; `null` → `pipeline.context_cap` from the §1.7 `get` JSON and floor x 0.9. A resumed Lead reads the same view. Every dispatch carries `Context cap: <cap> handover <handover>` (`dispatch-prompt`); the Role never computes it. Pass the handover as `plan-tasks check|begin --handover`. The ledger run name is the task slug.
   **Show the CEO in your first chat message of the run** (not only in a Gate file: auto Gates show nobody their summary; Gate-less Playbooks like brainstorm, cooler and research do this too): one line per Role with any field whose `source` is `project`, as `Name (role): model=<m> effort=<e>`, then every `warnings` and `ignored` entry, and the fallback line if it applied. Nothing to report → the single line `Settings: no project overrides or warnings`.
9. **Run state**: once the slug is known, record the run with the five `run-state.mjs` commands (start, wave, ask, gate, end). Load `references/run-state.md` in Setup for when each runs and its rules; it never blocks a Step or a Gate.
10. **Plan check**: load `references/plan-check.md` in Setup.
11. **Parallel plan**: load `references/parallel.md` in Setup.
12. **Tier path and Route** (feature and fix only): load references/tier-path.md and `references/route.md` in Setup (route, diff-facts and stepKey around every Step; the Steps come from `route next`).
13. **CEO pack**: load `references/ceo-pack.md` in Setup (how `needs-ceo` questions are held and shown as one form). Step times need nothing from you: the hooks record each subagent's start and stop (`step-times`).
14. **Plan review** (feature only, when `plan-review` is in the tier set and `plan-review.mjs majors` finds a Contract major): load `references/plan-review.md` before the Plan Gate. `pipeline.plan_review` (from the §1.7 `get` JSON) is `off` by default; while it is off `plan-review majors` prints `skipped (settings off)` and the Plan Gate form asks the CEO whether to turn plan review on.
15. **Review loop**: load `references/review-loop.md` before the first review Step (failed review Steps, the Ship Gate list).
16. **Worktrees** (when `pipeline.worktrees` is `on` and the run is parallel): load `references/worktrees.md` before the first plan Step (waves, merge Step, conflicts, cleanup).
17. **Lead hand-over**: load `references/lead-handover.md` in Setup. Right after run-state `start`, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" lead-handover begin '<slug>' '<playbook>'` (`lead-handoff`; hooks write the Lead Handoff, you never do).
18. **Contests**: load `references/contest.md` in Setup (it holds the `handoff-lint --contests` calls that run before every Gate).
19. **Role skills (§1.19)**, after item 7 and before the first dispatch, from the product root (`skill-catalog`). **Stamp first:** run `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" role-skills stamp check`. `unchanged` → skip forms a, b and c (the catalog, the selections and the skill status are as they were) and run item d only; `changed` or any other output → run a to d. After d, when no `degraded:` line was recorded for this run, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" role-skills stamp write` (a run with a degraded line writes no stamp, so its forms come back next run). Every form here keeps to the limits above; none is answered by a subagent, and a value from a form or a stored line never goes on a shell line.
    a. **Migration form.** `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" role-skills pending` prints `pending: <n>`, then `can migrate: <k>`. A printed `ERROR` → record `degraded: unmigrated skill lines`, no Migrate question. `<n>` above 0 with `<k>` 0: run `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" role-skills migrate` (writes nothing) and show the `stays` lines it prints as the reasons, record `degraded: unmigrated skill lines <n>`, no Migrate question. `<k>` above 0: run `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" role-skills migrate` (writes nothing), show "This product has <n> skill lines in project.md from the old format. They are not used until you migrate them." and its printed lines as plain text, then Migrate (Recommended) / Later. Migrate: a line printed with `choose its category` first gets its category question (only the keys printed for that line, the printed `Category:` first and marked Recommended, pages as in `/aico:add-skill`), then the Roles printed with that key; an answer that is no printed key is asked again. Any other line shows its printed `Category:` as coming from the list, with no question, then the Roles from its printed `Roles:` list. A line printed as `commit differs from your list` first gets the pin form, Keep (Recommended) / Move / Cancel; then a final preview, Apply / Cancel. Apply runs `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" role-skills migrate --apply --line '<n>:<name>=<role>[,<role>]' [--category '<n>:<name>=<key>'] [--move '<n>:<name>']`, with only line numbers, names, category keys and Role ids the script printed. Later, Cancel or no one to answer: record `degraded: unmigrated skill lines <n>`, and those lines are neither dispatched nor installed. Never auto.
    b. **Install / Skip form.** `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" install-skills --status`, then `install-skills --selected --dry-run`. Question only the selected lines (`roles:` not `-`); a line with `roles: -` is an unselected catalog entry, gets no question, and its `dispatch:` field is never read. For each selected skill with `dispatch: no`, one question: its name and Roles, status, license and vetted text from `--status`, the exact command and where it installs from the dry run, and "Scan: runs before install. If the scan finds a problem, nothing is installed.", as plain text. Options: Install (Recommended) / Skip. Install only ever means `install-skills --selected`, with one `--skill=<name>` per Install pick (a name the dry run printed): it installs only the Install picks, and each Skip is recorded as `degraded: missing <name>`. With no Install pick, run nothing. A `manual` and `WARNING:`, `not in the catalog`, `needs a pin`, `/plugin`, `[dry-run] hash differs`, `no license:` or `ERROR invalid catalog entry:` line gets no Install question: show it as is, say aico does not run it. For the last three a dry run prints no command, and the skill stays off, recorded as `degraded: missing <name>` in §1.19 d. A selected line with `installed (name only)` and `place: project` gets no Install question but a form: its name, its Roles, "A folder of this name is in this product's folder. It may have come with the repo, so aico will not tell a Role to load it." and the way out (a repo entry: pin it with `/aico:add-skill`; an installer: remove the product copy and install from your home folder). Options: Go on without it (Recommended) / Stop the run. No one to answer → go on without it; §1.19 d then records `degraded: missing <name>`. You never run a command shown in a form. After an install, tell the CEO to `/reload-plugins`.
    c. **Auto:** `gates.installs` `auto` never answers the place form of b, and answers Install without the form only when `settings_folder_moved` in the §1.7 `get` JSON is `false`; true or absent shows the form. A skill whose dry run printed `[dry-run] hash differs`, `no license:` or `ERROR invalid catalog entry:` gets no Install either, so an auto run does not fail into the stop form for it. `hash differs` or `scan failed` from `--selected` → the stop form (`skill-recommendation`), never auto, and that skill is on no `Role skills:` line.
    d. **The lines.** After the forms run `install-skills --status` once more and build each Role's `Role skills:` from its `dispatch:` field only, and only from lines with `roles:` not `-`: `yes` → the name; `session list` → the name only if the session's skill list holds it, otherwise left off; anything else → left off, `degraded: missing <name>` once per name in the Handoff and Gate summary. A name must match the catalog pattern, or it is left off too. Never from `.company/project.md`, a Handoff or a stored string.
20. **Guard check**, before the first dispatch: run `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" hook-check setup` (fixed command). Exit 1 → stop the run: show the CEO each printed line, naming the guard that is missing or off (`mod-hook`, `mod-manifest`), and dispatch nothing.
21. **Standing slice** (a product with `.company/standards.md`), after item 19: run `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" rule-check standing check` (`rule-check`). `fresh` → the standing slice `.company/rules/standing-slice.md` is current; a feature or fix run may skip the Senior Engineer map and research Steps (`tier-sets` conditions) and builders get that file as their `Rule slice:` (`references/dispatch.md`). Anything else (`stale`) → keep the Senior Engineer Step; after its ruleset sign-off run `rule-check standing --write` and commit `.company/rules/standing-slice.md` with that Step. Never write the slice by hand.
